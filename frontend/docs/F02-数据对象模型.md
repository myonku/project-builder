
# 数据对象模型

## 1. 文档定位

本文档是**前端 TypeScript 类型与后端契约的映射表**：哪些字段由哪个端点返回、哪些是派生字段、哪些"契约刻意不返回"。

- 字段**语义**以 [api/A01–A10](../../docs/api/README.md) 为准；
- 契约的**约定性叙述**（信封、分页、时间、错误码）以[《S02》](../../docs/S02-HTTP接口契约.md)§2 为准；
- 本文档只做"到 TypeScript 的翻译"与"跨端点共用结构的收敛"，**不新增契约**。
- **冲突以 S02 为准**：本文档与 S02 / api 冲突时，先改 api（或 S02），再改本文档。

**与前端其他文档的关系**：

- 技术栈、目录结构、Hook 约定 → [《F01 前端架构设计》](./F01-前端架构设计.md)；
- 运行、代理、构建、部署 → [《F03 运行与联调》](./F03-运行与联调.md)。

## 2. 通用类型

```ts
// 成功信封
export interface Envelope<T> {
  data: T;
  pagination?: Pagination;   // 只有列表端点有
}

export interface Pagination {
  page: number;
  page_size: number;
  total: number;
  has_next: boolean;
}

/** 列表端点的返回值：pagination 一定存在（client.ts 的 apiPostQuery / apiGetQuery 的返回类型） */
export interface Page<T> {
  data: T[];
  pagination: Pagination;
}

// 错误信封
export interface ErrorEnvelope {
  error: ErrorBody;
}

export interface ErrorBody {
  code: string;
  message: string;                        // 英文（S02 §2.4）
  fields?: Record<string, string>;        // 字段级明细；422 无明细时为 {}
  request_id: string;
}

/** 各域 *QueryBody 共用的分页与排序字段 */
export interface PaginationQuery {
  page?: number;                          // ≥1，默认 1
  page_size?: number;                     // 1–100，默认 20
  sort?: string;                          // "field" 升序 / "-field" 降序，逗号分隔
}
```

**落地位置**（骨架期）：这些通用类型在 `src/types/common.ts`；各资源类型按域拆成
`types/{auth,user,group,project,task,plan,attachment,reminder,audit}.ts`，**不设 barrel**
（`types/index.ts`）——域文件与 `api/` 的文件一一对应，直接 `import type { Project } from '@/types/project'`，
避免 barrel 带来的循环引用与打包时的隐式全量依赖。

**字段明细的实际语言**：`message` 是英文，但 `fields` 里的**明细文案是中文**
（实测：`sort` 报"不支持的排序字段 …，可用字段：…"）。因此 `fields` 可以直接回填到表单，
不需要再翻译（F04 C1）。

**约定**：

- `data` 是列表时后端保证空列表为 `[]` 而不是 `null`（《S02》§2.3）；前端类型用 `T[]`，**不要**写成 `T[] | null`。
- `fields` 只在**校验类错误**（422）与部分 409/403 上出现（例如 `fields.email`、`fields.role`）；其它情况省略。
- `request_id` 与响应头 `X-Request-ID` 一致；所有错误提示建议带上它。

### 2.1 与 MUI DataGrid 的对接约定

本文件的资源类型（`User`、`Group`、`Project`、`Task`、`Attachment`、`Reminder`、`AuditRecord`、各 `*Member`）**直接作为 `DataGrid<T>` 的泛型参数**，不需要额外包装或映射为"行模型"：

```tsx
import { DataGrid } from '@mui/x-data-grid';
import type { Project } from '@/types/project';

<DataGrid<Project>
  rows={rows}
  columns={columns}
  getRowId={(row) => row.id}
  loading={loading}
  paginationMode="server"
  sortingMode="server"
  filterMode="server"
  rowCount={rowCount}            // 来自 pagination.total
  paginationModel={paginationModel}
  onPaginationModelChange={onPaginationModelChange}
  sortModel={sortModel}
  onSortModelChange={onSortModelChange}
/>
```

**四条硬约定**：

1. **显式 `getRowId={(row) => row.id}`**。MUI 默认认 `id` 字段，但显式写更稳，也便于将来某些行类型（如没有 `id` 的临时行）单独处理。
2. **`paginationMode` / `sortingMode` / `filterMode` 全部设 `"server"`**。默认是 `"client"`，会让 DataGrid 在本地做一次分页/排序，与后端返回的数据口径不一致（表现为"后端返回 20 条、前端显示 1 页但 total 显示 100"）。
3. **`rowCount` 取 `pagination.total`**，**不要**用 `rows.length`。`rows.length` 是当前页条数；`rowCount` 是全量条数。二者混用在服务器模式下会导致分页条错乱。
4. **排序模型映射在 `useListQuery` 里完成**（见 F01 §5.4）：把 `SortModel`（`[{ field, sort }]`）序列化为后端的 `"field"` / `"-field"` 表达式字符串，并**按各域白名单硬校验**（未知字段 400）。**不要**把 DataGrid 的 `filterModel` 直接透传给后端——后端没有对应的表达式协议；筛选走各页面自己维护的表单状态。

**分页状态的两个坑**：

- MUI DataGrid 的 `paginationModel.page` **从 0 开始**，后端 `page` **从 1 开始**；`useListQuery` 里做 `±1` 换算，**不要**在组件里散落。
- `paginationModel.pageSize` 默认 `100`（DataGrid 自己的默认），后端默认 `20`、上限 `100`。初值必须显式设成后端默认值，否则"打开列表立刻打一次 `page_size=100` 的请求"会在后端日志里留下与你预期不符的记录。

## 3. 时间与日期

| 形态 | 例子 | TS 类型 | 约定 |
| --- | --- | --- | --- |
| 瞬时时间（UTC ISO 8601，**带亚秒**） | `"2026-10-11T04:30:54.047739Z"` | `string` | **原样透传**；展示时才格式化（见 F01 §5.1） |
| 瞬时时间（秒级 UTC） | `"2026-10-11T04:30:54Z"` | `string` | 同上 |
| 自然日 | `"2026-10-01"` | `string` | 不用 `Date` 对象 |
| 可空时间 | `null` | `string \| null` | — |

**重要**：`updated_at` 必须**原样回传**作为 `expected_updated_at`；截断到秒会让原子 CAS 必然失败（《S02》§2.6.2）。

**与 MUI 日期组件的配合**（`@mui/x-date-pickers`）：

- `<DatePicker>` 的 `value` 需要 `Dayjs` 对象，而本文件的 `start_date` / `end_date` 是 `string`。**转换只发生在字段边界**：进入组件前 `dayjs(str)`，`onChange` 时 `v?.format('YYYY-MM-DD')` 写回表单状态，**业务状态里始终是字符串**。
- **不要**把 `DatePicker` 的 `onChange` 直接接到提交逻辑上——时区换算会在跨零点时把日期带偏一天，且与 §5.1"原样透传"的原则冲突。
- 日期区间校验（`start_date <= end_date`）在前端**只做提示**，不做拦截（见 §9）；真正判定交给后端 `400 invalid_date_range`。

## 4. 公共资源表示

（与 `docs/api/README.md` §"公共资源表示"一致；此处只列前端 TS 定义。**派生字段标 `readonly`**。）

### 4.1 User（公开结构）

```ts
export interface User {
  id: string;                      // UUIDv7
  username: string;                // 保存为小写
  email: string;                   // 保存为小写
  display_name: string;
  status: 'active' | 'disabled';
  system_role: 'member' | 'admin';
  timezone: string;                // IANA
  reminder_enabled: boolean;
  last_login_at: string | null;
  updated_at: string;              // 版本字段
  avatar_updated_at: string | null; // 规划：非空表示有头像；用于缓存失效
}
```

**永不返回**：`password_hash`、会话令牌。前端类型里**不应该出现** `password` 相关字段。

> **2026-10-20 规划（未生效）**：`avatar_updated_at` 已先登记到 User 与各成员对象；
> 后端投影、A01/A02/A03/A04/A05/A06 契约尚未更新，落地前不要按此字段读取/构造头像 URL。
> 头像 URL 由 `UserAvatar` 用 `API_BASE + /users/{id}/avatar?v=<timestamp>` 生成，API 不返回完整 URL。
> 无上传头像时，前端按显示名首字生成彩色单字头像；`default-avatar.png` 只作兜底。

### 4.2 Group

```ts
export interface Group {
  readonly id: string;
  readonly name: string;                    // 1–160
  readonly description: string | null;      // ≤2000；未设置或已清空为 null
  readonly status: 'active' | 'disabled';
  readonly owner_id: string;                // 所有者（治理属性，不等同于成员角色）
  updated_at: string;                       // 版本字段
  readonly membership_role: 'member' | 'manager' | null;    // 派生：非成员为 null
  readonly membership_status: 'active' | 'removed' | null;  // 派生：非成员为 null
}
```

**注意**：

- `readonly` 在本文件里表示"客户端不得写入该字段"，与"响应里一定存在"是两件事。`id` / `name` 等本来就不该由前端改，标 `readonly` 只是为了在构造请求体时避免误用响应对象（比如 `{...group}` 直传 PATCH）——后端对未知字段会 422，但对**已知但不可改**的字段（如 `id`）也会有各自的处理。**提交前一律用 §6 的 `*Body` 类型**，不要用响应类型当请求体。
- `membership_role` **没有** `owner`。工作组所有者由 `owner_id` 表达；成员行里的 `role` 只有 `member` / `manager`（见 §4.5）。

### 4.3 Project

```ts
export type ProjectStatus =
  | 'not_started' | 'in_progress' | 'paused'
  | 'completed'   | 'archived'    | 'cancelled';

export type ProjectVisibility = 'private' | 'group_readonly' | 'group_editable';

export interface Project {
  readonly id: string;
  readonly name: string;                    // 1–200
  readonly group_id: string;                // 必须且只能归属一个组
  readonly description: string | null;      // ≤4000
  readonly created_by: string;              // ≠ 持有者（持有者由 members 里 role='owner' 决定）
  readonly status: ProjectStatus;
  readonly visibility: ProjectVisibility;
  readonly start_date: string;              // YYYY-MM-DD
  readonly end_date: string;                // YYYY-MM-DD
  readonly color: string | null;            // ≤32，自由文本（如 "#336699"）
  readonly archived_at: string | null;      // 非空即视为归档（与 status 一起判定）
  readonly progress: number;                // 派生：有效任务进度简单平均
  readonly overdue_task_count: number;      // 派生：按请求者时区算"今天"
  readonly membership_role: 'owner' | 'member' | null;   // 派生：非成员为 null
  updated_at: string;                       // 版本字段
}
```

**刻意不返回**（前端**不要**定义这些字段）：`created_at`、`is_archived`、`is_read_only`、`my_role`、`owner_id`、`task_count`。它们只出现在**计划视图**的投影里（见 §5）。

- 判断归档：`status === 'archived' || archived_at !== null`。
- 要拿持有者：查成员列表里 `role === 'owner'` 的那条。
- **PATCH 前先拆出可写字段**：`const { updated_at, progress, overdue_task_count, membership_role, created_by, id, ...writable } = project;`——`writable` 才是可以进 `UpdateProjectBody` 的部分。这一步可以放进 `useVersionedForm` 的 `buildPatch()` 里，不必每个页面手写。

### 4.4 Task

```ts
export type TaskStatus = 'not_started' | 'in_progress' | 'completed' | 'cancelled';
// 没有 'overdue'：逾期是派生字段 is_overdue

export interface Task {
  readonly id: string;
  readonly project_id: string;
  readonly parent_id: string | null;        // 最多 3 层
  readonly created_by: string;              // 不随持有者转移而变
  readonly name: string;                    // 1–200
  readonly description: string | null;      // ≤4000；更新时空串存 ""
  readonly status: TaskStatus;
  readonly progress: number;                // 0–100
  readonly priority: 0 | 1 | 2 | 3;         // 低/普通/高/紧急
  readonly start_date: string;
  readonly end_date: string;
  readonly is_milestone: boolean;
  readonly is_shared: boolean;              // 决定能否进组内视图
  readonly is_overdue: boolean;             // 派生
  readonly deleted_at: string | null;       // 逻辑删除
  readonly membership_role: 'owner' | 'member' | null;   // 派生；非任务成员为 null
  readonly updated_by: string;              // 最近一次修改本任务行的用户
  updated_at: string;                       // 版本字段
}
```

**刻意不返回**：`updated_by_name`（只在计划视图提供）、`can_edit` / `is_read_only` / `my_role` / `owner_id` / `members` / `summary`（这些是计划视图的投影）、`created_at`、子任务数组、附件。

**PATCH 前的可写字段**：`UpdateTaskBody` 的键集合（见 §6.4）——其余键（含 `updated_at`、`is_overdue`、`membership_role`、`deleted_at`）都不是可写字段。同样交给 `useVersionedForm` 处理。

### 4.5 成员关系对象

```ts
export interface GroupMember {
  readonly id: string;
  readonly group_id: string;
  readonly user_id: string;
  readonly role: 'member' | 'manager';      // 没有 'owner'：所有者由 groups.owner_id 表达
  readonly status: 'active' | 'removed';    // 软移除
  readonly joined_at: string;
  readonly username: string;
  readonly display_name: string;
  readonly email: string;                   // 写响应里为 ""（见《A03》§6/§7）
  readonly avatar_updated_at: string | null; // 规划
}

export interface ProjectMember {
  readonly id: string;
  readonly project_id: string;
  readonly user_id: string;
  readonly role: 'owner' | 'member';        // 恰好一个 owner
  readonly username: string;
  readonly display_name: string;
  readonly email: string;
  readonly avatar_updated_at: string | null; // 规划
}

export interface TaskMember {
  readonly id: string;
  readonly task_id: string;
  readonly user_id: string;
  readonly role: 'owner' | 'member';        // 恰好一个 owner
  readonly username: string;
  readonly display_name: string;
  readonly email: string;
  readonly avatar_updated_at: string | null; // 规划
}
```

**注意**：

- 项目/任务成员**没有 `status`**——移除即删行；工作组用软移除（`status: 'removed'`）。
- 工作组**写接口**（添加/改成员）返回的 `username` / `display_name` / `email` 是**空字符串 `""`**（《A03》§6、§7 备注）；要展示用户信息请用成员列表或 `GET /users/{id}`。
- 因为这三个成员对象**没有可写字段**（角色变更走 §6.2 / §6.3 / §6.4 的专用请求体），所以整体标 `readonly` 是安全的；`DataGrid<GroupMember>` 这种用法不会因为 `readonly` 而受影响。

### 4.8 Reminder

```ts
export type ReminderKind =
  | 'task_assigned' | 'task_start_soon' | 'task_due_soon'
  | 'task_overdue'  | 'task_owner_changed';

export type ReminderStatus = 'pending' | 'sent' | 'failed' | 'skipped';

export interface Reminder {
  readonly id: string;
  readonly task_id: string;
  readonly recipient_id: string;
  readonly recipient_email: string;         // 生成时刻的快照
  readonly kind: ReminderKind;
  readonly kind_label: string;              // 中文说明，可直接展示
  readonly scheduled_for: string;           // 计划发送时刻（UTC，可能带亚秒）
  readonly status: ReminderStatus;
  readonly attempts: number;                // 成功/失败/跳过都各计一次
  readonly last_error: string;              // 成功时为 ""（不是 null）
  readonly sent_at: string | null;
  readonly created_at: string;
  readonly updated_at: string;
}
```

**不返回** `dedupe_key`。

**`status` 语义**（《A08》）：

| `status` | 含义 | 可重试 |
| --- | --- | --- |
| `pending` | 在队列中 | 否（409） |
| `sent` | 已发送成功 | 否（409） |
| `failed` | 发送尝试失败，需排查 | 是 |
| `skipped` | 按规则就不该发（无邮箱/停用/关闭提醒/邮件未启用等） | 是 |

**整对象 `readonly` 的理由**：唯一能改提醒的端点是 `POST /reminders/{id}/retry`（无请求体），没有可写字段。因此标 `readonly` 不会挡住任何合法操作。

## 5. 计划视图的投影

计划视图（《A06》）返回的项目/任务投影与 §4 的 Project/Task **不完全相同**。

### 5.1 差异一览

| 差异 | Project | Task |
| --- | --- | --- |
| 额外字段 | `is_archived`、`is_read_only`、`owner_id`、`my_role`、`task_count` | `can_edit`、`owner`、`members`、`updated_by_name` |
| 缺字段 | `created_by`、`membership_role`（换成 `my_role`） | `created_by`、`deleted_at`、`membership_role` |

```ts
  readonly can_edit_tasks: boolean;
  readonly tasks: PlanTask[];
  readonly summary: PlanSummary;            // project_count 恒为 1
}
```

**为什么整个计划视图对象都标 `readonly`**：计划视图是**只读投影**——修改走的是 §4 的 `/projects/*` 与 `/tasks/*` 端点，它们各自返回 Project / Task（不是 PlanProject / PlanTask）。把整个投影标 `readonly` 能防止"拿 PlanTask 直接 PATCH"这类错误（字段集合与 `UpdateTaskBody` 并不相同）。

**但有一处例外需要注意**：第二版甘特图拖拽改日期时，前端会把 `PlanTask.start_date` / `end_date` 和 `updated_at` 取出来拼 `UpdateTaskDatesBody`（`@mui/x-data-grid` 之外的组件）。这属于**读取**而非写入 `PlanTask`，`readonly` 不妨碍：

```ts
const body: UpdateTaskDatesBody = {
  start_date: task.start_date,   // 读取没问题
  end_date: task.end_date,
  expected_updated_at: task.updated_at,
};
```

（《A06》§"三个视图的差异一览"）

| | 个人计划 | 组内计划 | 项目甘特图 |
| --- | --- | --- | --- |
| `data` 顶层 | `group_id` / `projects` / `tasks` / `summary` | 同左，`group_id` 为组 id | `project` / `can_manage_project` / `can_edit_tasks` / `tasks` / `summary` |

## 6. 请求体类型

这些是各写端点接收的请求体。**契约字段集合严格**：出现未定义字段会返回 `422 validation_error`（《S02》§2.7）。

**与 React Hook Form 的配合约定**：

- `*Body` 类型直接作为 `useForm<UpdateProjectBody>()` 的泛型参数；**字段集合一致**，不要另立一份"表单类型"再手工同步，那一定会分叉。
- 所有 `*Body` 里的 `expected_updated_at` 标 `readonly`：它**不是用户可编辑字段**，由 `useVersionedForm` 在构造请求体时注入。表单 UI 里**不应**出现对应输入框（无 `<TextField>` 绑定它）。
- **骨架期的验证结论**：`readonly` 不会挡住任何合法用法。`useVersionedForm.save(patch)` 接收的是
  `Omit<TBody, 'expected_updated_at'>`，内部拼成 `{ ...patch, expected_updated_at: version }` 后一次性提交，
  全程不需要 React Hook Form 去 `setValue('expected_updated_at', ...)`。
  因此本节原先设想的 `setValue('expected_updated_at' as never, ...)` 或"把 readonly 去掉"两种绕法**都不需要**；
  如果将来真要在表单里注入版本字段，再按需放开类型，**不要**用 `as never` 绕开类型系统。

## 8. 派生字段总表

下列字段**不持久化**、由查询计算，客户端**不得写入**（提交它们会因"未知字段"返回 422）。**在本文件的类型定义里一律标 `readonly`**——这是把"不得写入"从文档约定变成编译期约束。

| 字段 | 归属 | 规则 |
| --- | --- | --- |
| `progress` | Project | 有效任务进度简单平均；已取消与已逻辑删除不参与；无有效任务为 `0` |
| `overdue_task_count` | Project | `end_date < 今天` 且状态 `not_started` / `in_progress` 的任务数 |
| `is_overdue` | Task | 同上，按**请求者时区**算"今天" |
| `membership_role` | Group / Project / Task | 当前请求者在该对象中的成员角色；非成员为 `null` |
| `membership_status` | Group | 请求者成员关系状态（`active` / `removed`）；非成员为 `null` |
| `is_archived` / `is_read_only` | PlanProject | 归档判定与只读投影 |
| `my_role` | PlanProject | 计划视图里的 `membership_role` 别名 |
| `task_count` | PlanProject | **本视图内可见**的任务数（可能小于项目详情口径） |
| `can_edit` | PlanTask | 归档项目恒为 `false`；组内只读共享同样 `false` |
| `owner` / `members` | PlanTask | 已按"持有者优先、显示名"排序 |
| `updated_by_name` | PlanTask | 服务端 JOIN 取出，前端不必再查用户 |
| `kind_label` | Reminder | 提醒类型的中文说明，可直接展示 |
| `can_manage_project` / `can_edit_tasks` | GanttPayload 顶层 | 与逐任务 `can_edit` 配合使用；**`can_manage_project` 对系统管理员可能为 `false`**（《A06》§3 备注），不要用它做权限判定的唯一依据 |

**三条硬约定**：

1. **不提交派生字段**。类型上把它们标成 `readonly`，从源头上防住误提交。
2. **`is_overdue` / `overdue_task_count` 优先用后端值**。前端也能算，但两边算法分叉时后端为准（《S02》§5 加强项：按请求者时区）。
3. **`membership_role` / `my_role` 只用于展示，不用于权限判定**。真正决定"能不能改"的是：
   - 项目：`GET /projects/{id}` 的 `membership_role` 是否为 `owner`，**或**当前用户 `system_role === 'admin'`；
   - 任务：项目是否可写 + 任务 `is_shared`（按 F01 §6 第 8 条）；
   - 归档：`project.status === 'archived' || project.archived_at !== null`（F01 §6 第 7 条）。
   把这些判定集中放进 `usePermission`（F01 §3），**不要**散落在各页面。

## 9. 前端不做运行时校验的字段（由后端兜底）

这些字段前端**做基础类型约束即可**，不在客户端重复实现后端的规则——重复实现迟早分叉：

- 名称长度、`description` / `color` 上限；
- 日期区间（`start_date <= end_date`）；
- 父任务层级与区间覆盖；
- 状态与进度的联动推导（`progress` 未给 `status` 时后端推导）；
- 唯一持有者约束、至少一个启用中管理员；
- `expected_updated_at` 的等值比较（客户端只负责原样回传）。

**Zod 的边界**：只做**结构校验**（字段是字符串/数字/布尔、必填是否缺失、UUID 格式），不做**语义校验**（长度、区间、联动）。语义判定全部交给后端，并通过 `useApiError`（F01 §5.2）把 `422 fields` 回填到 React Hook Form 的 `setError()`。

**唯一例外**是"归档只读"：前端**必须**提前禁用编辑入口（见 F01 §6 第 7 条），因为那是高频交互，每次撞 409 会很难用。这条不是"重复实现后端规则"，而是**UX 前置条件**——禁用入口的依据是响应里已有的 `status` / `archived_at`，不需要额外推导。
