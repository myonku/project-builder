### 5.2 未登录 / 未启动后端时的行为

```text
GET http://127.0.0.1:5173/api/v1/auth/me   → 502（Vite 代理 ECONNREFUSED 127.0.0.1:8000）
```

说明代理链路已经生效；此时前端应停在登录页并给出可读提示，而不是白屏——由
`stores/auth.ts` 的 `loadMe`（网络错误与 401 都归到 `anonymous`）+ 登录页的提示条承担。

### 5.3 认证与信封（**经 Vite 代理**，即浏览器看到的那条路径）

| 请求 | 期望 | 实测 |
| --- | --- | --- |
| `POST /api/v1/auth/login`（正确口令） | 200 + `Set-Cookie` | 200，`data` 为 `User`，Cookie `pb_session`（`HttpOnly=True`） |
| `GET /api/v1/auth/me`（带 Cookie） | 200 | 200，返回同一用户 |
| `GET /api/v1/auth/me`（无 Cookie） | 401 `authentication_required` | 401，`{error:{code,message,request_id}}` |
| `POST /api/v1/auth/login`（错误口令） | 401 `invalid_credentials` | 401，文案不区分"账号不存在"与"密码错误" |
| `POST /api/v1/auth/logout` | 204 | 204 |
| 退出后再 `GET /auth/me` | 401 | 401 |
| `POST /api/v1/projects/query` | 200 + `pagination` | 200，`pagination:{page:1,page_size:20,total:2,has_next:false}` |
| `POST /api/v1/projects/query`（`sort=not_a_field`） | 400 `invalid_request` | 400，`fields.sort` 给出可用字段清单 |
| `POST /api/v1/projects/query`（`page_size=500`） | 400 `invalid_request` | 400，`fields.page_size` |
| `GET /api/v1/projects/{不存在的 uuid}` | 404 `project_not_found` | 404 |
| `GET /api/v1/plan-views/personal` | 200 | 200，`projects/tasks/summary` 结构完整 |
| `GET /api/v1/plan-views/personal?bogus=1` | 400 `invalid_request` | 400，`fields.bogus` 列出可用参数 |
| `POST /api/v1/auth/login`（带未定义字段） | 422 `validation_error` | 422，`fields.unexpected_field`（中文明细，见《F04》C1） |
| `POST /api/v1/users/query`（`include_disabled=true`） | 200 | 200 |

**结论**：`api/client.ts` 的信封解包、Cookie 传递、错误码分支所依赖的**每一条实测行为**都与
《S02》§2.3 / §2.4 / §2.5 一致；`useApiError` 的映射表因此可以直接按状态码实现。

### 5.14 表格悬浮提示统一（用户反馈）

| --- | --- | --- | --- |
| 项目列表 | 工作组 / 结束日期 / 进度 / 最近更新 | 有 | 无 |
| 项目列表 | 状态（归档时间）/ 操作 | 无 | 有 |
| 邮件列表 | 类型 / 计划发送 / 发送时刻 | 有 | 无 |
| 邮件列表 | 收件人 / 失败原因 / 状态提示 / 操作 | 无 | 有 |

**修法（F04 D33 方案 3）**：新增 `components/common/DataTooltip.tsx`（外观常量 + `DataTooltip` + `textCell()` 工厂）；
四张表的文本类列改用 `textCell()`（**写了 `renderCell` 才会去掉原生 `title`**）；单元格内的显式提示改用 `DataTooltip`；
`TruncatedText` 共用同一份样式常量。

### 5.21 筛选下拉默认项显示修复（2026-10-19）

“上级任务”默认“（顶层任务）”也补了同一设置。计划页保持原实现不变。

### 7.5 自助注册审核链路（评估与实现记录，2026-10-19）

**评估结论**：原后端不支持“提交注册申请 → 管理员审核 → 放行”的链路，必须先改后端接口。
该改造已于同日完成，实际实现与验证见 **§5.22**；本节保留评估依据，便于追溯。

**评估时的事实（现已变更）**：

- `POST /auth/register` 直接创建 `status=active` 的用户并返回 201，不建立会话（《A01》§1）；
- `users.status` 的数据库 CHECK 只有 `active` / `disabled`，**没有 `pending`**；也没有 `registration_requests` 一类申请表；
- `POST /users/query` 只有 `include_disabled`，没有“待审核”过滤；
- 管理员侧只有 `PATCH /users/{id}`（可改 `status`）与 `POST /users/{id}/disable`，**没有 approve / reject 端点**；
- `group_join_requests` 是“已有账号申请加入工作组”，不能拿来做账号注册审核（它要求 `user_id` 已存在）。

因此在评估时，用旧接口只能做到“注册即 active”，或“注册后管理员再去用户列表手动停用”，
都表达不了“待审核”和“拒绝”，不能作为审核链路。

**后来采用的后端改造（已实现）**：

1. **新增迁移 `000006_registration_requests`**：申请表至少包含
   `id`、`username`、`email`、`display_name`、`password_hash`（**只存摘要，不存明文**）、`timezone`、
   `status`（`pending` / `approved` / `rejected`）、`reviewed_by`、`reviewed_at`、`rejection_reason`、
   `created_at` / `updated_at`。对 `lower(username)` / `lower(email)` 建“仅 pending 唯一”的部分唯一索引，
   通过/拒绝后允许重新申请；通过时在同一事务内再检查 `users` 唯一约束。
2. **公共入口改为提交申请**：`POST /auth/register` 不再创建用户，返回 `202` + 申请 id/`status: pending`，
   不建会话、不返回 Cookie。这样只有一个公共入口，不会被绕过。**注意**：这会改变 A01/S02 的现有语义，
   若要保留旧接口，必须明确废弃/限制旧入口，不能同时保留一个“直接 active”的公共注册口。
3. **管理员接口**（均要求系统管理员）：
   - `POST /registration-requests/query`：`{status?, page?, page_size?, sort?}` → 申请列表 + `pagination`；
     响应**绝不返回** `password_hash`；
   - `POST /registration-requests/{id}/review`：`{status: 'approved' | 'rejected', reason?}`；
     通过时创建 `active` 用户（复用注册的归一化/密码校验/唯一性逻辑）并标记申请，拒绝时只标记；
     返回 `{request, user?}`；非 `pending` 或身份已被占用返回 `409`；
   - 建议同时提供 `GET /registration-requests/{id}` 供审核详情；如果列表已带全字段，可省。
4. **审计**：最低限度可在“通过”时写现有 `user/created`；完整留痕建议新增
   `registration_request` 对象类型与 `approved` / `rejected` 动作，但这会改动
   `activity_logs` 的 CHECK、`domain/audit.go` 白名单与 A09，需一起做迁移与测试。
5. **文档同步**：S01（注册需审核）、S02（注册语义、403/404/409）、A01（register 改为申请）、
   A02 或新增 A10（审核接口）、A09（若新增审计对象类型）、B02（迁移）、B04/B05（偏离与验证）、
   F01/F02/F03/F04/F05（前端类型、接口、路由与进度）。

**前端实现（已落地，详见 §5.22）**：

- 公共 `/register` 页面：复用 `sign-up` 模板的表单字段（`username` / `email` / `display_name` /
  `password` / 可选 `timezone`），提交后展示“申请已提交，等待管理员审核”，**不自动登录**；
- 管理员审核页：建议独立路由 `/admin/registration-requests`，与 `/admin/users` 并列放在“系统管理”下；
  若要做成用户管理的二级菜单，可把“用户管理”做成可折叠分组，子项为“用户列表 / 注册申请”。
  **不推荐**把“用户列表 + 注册申请”上下拼在同一个页面：两者的分页、筛选和动作完全不同，拼在一起会让
  `useListQuery` 的状态互相干扰；
- 审核列表用 `useListQuery`，列建议：用户名 / 显示名 / 邮箱 / 时区 / 申请时间 / 状态 / 操作
  （通过、拒绝）；拒绝可填原因；操作成功后刷新列表并提示；
- 新增 `types/registration.ts`、`api/registration.ts`，并复用 `useApiError` / `useDialogs` / `useNotifications`。

**替代方案（不推荐）**：直接给 `users.status` 增加 `pending`。这样不用新表，但待审核账号会混进用户表，
拒绝后只能落成 `disabled`（没有拒绝原因），且 pending 行会占用用户名/邮箱唯一约束；还要改
`UserStatuses`、用户列表口径、登录错误语义和大量测试。除非后端明确要极简实现，否则优先用独立申请表。
