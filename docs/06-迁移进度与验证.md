# 迁移进度与验证

## 1. 文档定位

本文档记录 Go 重写的**阶段状态**、**验证方法与可复现证据**、**契约覆盖矩阵**与**剩余工作**。
它是 Python 版本 `backend/服务端推进计划.md` 的对应物，但采用更严格的完工判定：
**只有真实依赖上的验证结果才构成交付依据。**

原始报文核对（`Invoke-WebRequest` 直读，未经 PowerShell 对象转换）：

```json
{"data":{"id":"01a1290b-0ae8-7046-9106-30f2d07815af","username":"wire_113911",
```

### 6.2 不满足即不交付的红线（承接到后续阶段）

以下条件必须持续成立，任何阶段都不得突破：

1. 不得用空路由或仅返回成功的占位实现冒充"已实现"。
2. 不得以"单元测试通过"作为交付依据；涉及 SQL 或约束的改动必须有真实数据库验证。
3. 不得在 handler 中复制权限规则或拼接 SQL。
4. 不得向客户端泄漏堆栈、SQL、物理路径或敏感值。
5. 不得引入未被使用的抽象层。

## 7. 剩余工作

### 7.1 第二阶段：Groups / Projects / Tasks

按依赖顺序实现，每个域先补契约细节，再迁移（如需要）、再 Service/Repository、最后 API 与测试。

**Groups**

- 组、成员、加入申请三条链路与状态机。
- 明确 `groups.owner_id` 唯一性差异：当前仅由应用层保证，数据库无约束
  （见《02-数据库模型与迁移.md》3.2）。第二阶段需决定补数据库约束还是显式声明差异。

**Projects**

- 项目生命周期、共享级别、成员管理与派生统计（`progress`、`overdue_task_count`）。
- `PATCH` 必须实现原子 CAS（契约 2.6）并覆盖版本冲突测试。
- 项目成员可来自归属组以外的其他工作组。

**Tasks**

- 任务、成员、父子层级（最多 3 层）、状态、日期、进度、逻辑删除。
- **必须**覆盖组合筛选（`owner_id` + `assignee_id` 双别名 JOIN）。
- **必须**覆盖逻辑删除在单查与列表两条路径上行为一致。
- `is_overdue` 为派生字段，按用户时区计算，不持久化。
- `Idempotency-Key` 在 `POST /tasks/{id}/copy` 上接入并覆盖重复请求测试。

**横切**

- 列表分页：`page >= 1`、`page_size <= 100` 服务端强制；SQL 层 `LIMIT/OFFSET`；
  排序白名单 + `id` 次级键；未知筛选/排序字段返回 400。
- 审计（`activity_logs`）与提醒生成的"事务提交后触发"边界。

### 7.2 第三阶段：Plan Views / Attachments / Reminders / Audit

- **Plan Views**：先定"归档 / 逻辑删除对象是否可见"的可见性规则。
- **Attachments**：multipart、流式大小限制、权限继承、逻辑删除后访问规则、扩展名白名单。
- **Reminders**：状态机、`dedupe_key`、Redis 锁、提交后触发、工作日计算、单实例调度、SMTP 适配。
- **Audit**：统一动作命名、敏感字段过滤、写入时机。

### 7.3 第四阶段：交付收口

- 端到端验收：注册 → 工作组 → 项目 → 任务 → 共享视图 → 附件 → 提醒 → 审计。
- Mailpit 与存储适配器的集成测试。
- 日志脱敏审计、备份恢复说明、部署验收。
- 生产 CORS、HTTPS、Cookie `Secure`、密钥轮换配置核对。
