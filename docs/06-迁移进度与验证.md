# 迁移进度与验证

## 1. 文档定位

本文档记录 Go 重写的**阶段状态**、**验证方法与可复现证据**、**契约覆盖矩阵**与**剩余工作**。
它是 Python 版本 `backend/服务端推进计划.md` 的对应物，但采用更严格的完工判定：
**只有真实依赖上的验证结果才构成交付依据。**

```powershell
pwsh -File ./scripts/smoke.ps1 -BaseUrl http://127.0.0.1:8099
```

结果：**117 项断言全部通过**（第一阶段 30 项 + 第二阶段 32 项 + 第三阶段 55 项：
用户资料可见性、跨用户修改权限、空更新拒绝、未知字段拒绝、字段逐个生效、邮箱唯一性、
停用端点权限、版本冲突与过期版本；管理员端点的权限与参数边界；
**以及管理员端点的成功路径——引导管理员登录、创建用户、列表、重置密码、新密码生效**）。
退出码 `0`。

> **引导管理员是冒烟覆盖管理员成功路径的前提**：服务以 `make run-test-config` 启动时
> 会按 `security.bootstrap_admin_*` 初始化一个系统级后台账号（见《03-配置与运行.md》3.6.1）。
> 该初始化只在**启动时**执行一次，因此若在服务运行期间跑过集成测试
> （测试会 TRUNCATE 业务表，把引导管理员一并删掉），需要重启服务再跑冒烟。
> 冒烟脚本在管理员登录失败时会直接给出这条提示。

```text
=== 健康检查 ===
  [PASS] GET /api/v1/health/live = 200
  [PASS] 缺少 arg 头被拒绝：422
  [PASS] GET /api/v1/health/check (带 arg 头) = 200
  [PASS] GET /api/v1/health/ready = 200
=== 会话网关：未登录访问受保护端点 ===
  [PASS] GET /api/v1/auth/me（无 Cookie） = 401
  [PASS] error.code = authentication_required
  [PASS] 错误信封包含 request_id
=== 注册 ===
  [PASS] POST /api/v1/auth/register = 201
  [PASS] 返回用户 id / updated_at
  [PASS] 响应未泄漏密码或摘要
=== 重复注册应 409 ===        [PASS] 409 / conflict
=== 字段校验应 422 ===        [PASS] 422 / validation_error，带 4 个字段明细
=== 登录（凭据错误） ===      [PASS] 401 / invalid_credentials
=== 登录（成功） ===          [PASS] 200，会话 Cookie 带 HttpOnly
=== 当前用户（已登录） ===    [PASS] 200，data.id 与注册一致，last_login_at 非空
=== 登出 ===                  [PASS] 204；(登出后) 401
```

原始报文核对（`Invoke-WebRequest` 直读，未经 PowerShell 对象转换）：

```json
{"data":{"id":"01a1290b-0ae8-7046-9106-30f2d07815af","username":"wire_113911",
"email":"wire_113911@example.com","display_name":"Wire","status":"active",
"system_role":"member","timezone":"UTC","reminder_enabled":true,
"last_login_at":null,"updated_at":"2026-10-11T03:39:11Z"}}
```

```json
{"error":{"code":"authentication_required","message":"Authentication is required.",
"request_id":"5d96353a3b75b7ce2371cbfa004f5e5a"}}
```

响应头：`X-Request-ID` 存在且与信封 `request_id` 一致；`Content-Type: application/json; charset=utf-8`。

结论：`updated_at` 为 `Z` 结尾的 UTC ISO 8601；错误信封形状与契约 2.4 逐字段一致；
**不存在** Python 版本的 RFC7807（`{type,title,status,detail,instance}`）混用问题。

### 5.7 变异验证：证明这些用例真的有鉴别力

"测试通过"本身不构成证据——一个在缺陷存在时仍然通过的用例只会带来虚假的安全感
（本阶段实测到了这一点，见 5.8 第 2 条）。因此第三阶段对关键实现逐条注入缺陷，
确认对应用例**确实失败**：

| # | 注入的缺陷 | 拦住它的用例 | 结果 |
| --- | --- | --- | --- |
| 1 | `UpdateProfileParams` 漏传 `Email`（字段在参数搬运处被丢弃） | `TestUserProfileUpdateAppliesEveryProvidedField` | ✅ 失败 |
| 2 | `NormalizeUserProfileUpdate` 把已提供的 `email` 置为 `nil` | 同上（由 `assertNotDropped` panic 拦住） | ✅ panic |

> 于是缺陷被记为"没被拦住"。**验证脚本本身也会说谎**，它同样需要被核对
> （这与 5.8 第 3 条是同一类问题）。

### 5.8 第三阶段开发中发现并修掉的问题

| # | 问题 | 表现 | 发现者 |
| --- | --- | --- | --- |
| 1 | `tasks.Handler.today()` 直接读 `time.Now()`，绕过了注入的时钟 | 派生字段 `is_overdue` 与真实日期绑定，使用固定时钟的测试**无法锁定它**；"按用户时区计算今天"也无处接入。修复方式是把计算移入 `tasks.Service.TodayFor`，使用注入时钟与 actor 时区 | 接入用户时区时发现 |
| 2 | 首版并发用例**没有鉴别力** | 去掉守卫里的 `FOR UPDATE` 后用例依然通过：两个请求被调度成一先一后，数据库层面从未真正重叠。修复方式是先用独立会话占住行锁**强制交错**，并另加一条"只锁另一个管理员"的用例精确隔离守卫是否取锁 | 变异验证（5.7 第 10 条） |
| 3 | 冒烟检查**打到了旧进程** | 管理端点的全部断言返回 404：`job_kill` 只结束了外层 shell，`bin/api.exe` 子进程仍占着 8099 端口，新构建的二进制绑定失败并以 1 退出，于是冒烟请求被旧二进制处理。修复方式是**按 PID 结束监听进程**再重启，并核对"端口空闲"后才启动 | 冒烟检查（11 项意外失败） |

第 2 条比第 1 条更值得记住：它说明**并发正确性不能用"并发跑一次恰好通过"来证明**。
第 3 条则说明**"验证跑过了"不等于"验证跑在正确的对象上"**——两者都已写入 6.4 的红线。

### 6.4 不满足即不交付的红线（承接到后续阶段）

以下条件必须持续成立，任何阶段都不得突破：

1. 不得用空路由或仅返回成功的占位实现冒充"已实现"。
2. 不得以"单元测试通过"作为交付依据；涉及 SQL 或约束的改动必须有真实数据库验证。
3. 不得在 handler 中复制权限规则或拼接 SQL。
4. 不得向客户端泄漏堆栈、SQL、物理路径或敏感值。
5. 不得引入未被使用的抽象层。
6. 归一化/校验函数接收"部分字段"结构体时，必须断言已提供的字段没有被静默丢弃
   （见 5.5 第 5 条）。
7. **不得用"并发跑一次恰好通过"充当并发正确性的证据**。并发类断言必须满足其一：
   用外部会话占住行锁等方式让交错**确定发生**，或经变异验证证明它在缺陷存在时确实失败
   （见 5.8 第 2 条）。
8. **验证必须跑在正确的对象上**。启动服务做端到端验证前，先确认端口由新构建的进程持有：
   结束后台任务不等于结束其子进程，旧二进制会继续服务请求，让"验证通过"变成
   对上一版产物的验证（见 5.8 第 3 条）。变异验证同理：先确认被测用例真的在
   所选包内被执行，否则"没有匹配用例"也会被误读成"用例没拦住"。
