## 3. 跨端固定边界

- 产品面向内部网络。品牌只改变用户可见展示；Go module、数据库名、包名、会话 Cookie 等技术标识保持现有值。登录/注册顶栏 W 图标、卡片 W + Worklane + tagline；WILT 位图保留作历史备用，不是当前字标。
- PostgreSQL 管业务元数据与权限，Redis 管会话/限流，Mongo GridFS 或 local 存字节。保留 local 作迁移/回退来源，不常驻双读/双写；迁移后切 GridFS 前必须完成校验，回退先反向复制。运行与备份命令以 B03 为准。
- 头像接口仅 PNG/JPEG，独立于附件配额；可见性与用户资料一致。注册不生成头像对象，UserAvatar 处理默认图、首字及失败回退。前端裁剪不改变服务端校验或头像缓存/版本规则。
- 密码重置策略、令牌与会话失效规则以 A01/A02 为准；管理员重置也吊销会话。当前同步 SMTP 的响应计时差异是已登记的内部网络 MVP 取舍，不把异步发送写成已完成。
- 工作组目录对登录用户开放启用组的基本资料和本人状态；详情/成员/组内计划权限保留。本人申请每组一条最新记录，重新申请更新原记录；停用组不再被发现，但申请仍保留可见。
- 附件没有独立权限，始终继承所属项目/任务；本人管理页不授予额外清理权限。逻辑删除保留对象和配额，彻底删除需确认并先逻辑删除，既有端点实时重新校验权限。
- 现行需求在 S01，HTTP 在 S02/A，架构/运行在 B/F；本页只统筹、索引及说明全局取舍，不复制成第二份字段或配置规范。

### 5.1 层级任务逐层汇总实施计划（2026-10-27 修订）

**实施状态更新（2026-10-27）**：下述功能阶段已完成，新分支 `codex/hierarchical-task-rollup` 已分阶段提交。真实依赖全量验收 359 顶层 / 955 含子用例通过、0 失败、0 测试跳过，HTTP 冒烟 207 项通过，桌面/手机浏览器通过。迁移 000010、代码与前端已交付；步骤 4 中最终设计/接口/架构说明文档同步按用户要求另行安排，本轮只记录实施边界和验收证据，不将设计同步列为本轮未完成项。证据见 B05/F05 文末。下文“本轮只修订规划”等表述保留原规划轮的历史范围。

**确认的方向与本轮范围**：层级表示工作拆分，采用“叶子节点手动维护，直接下级等权汇总，逐层向上传递到项目”。本节替换 2026-10-26 的项目平铺汇总方案；本轮只修订规划，不修改代码、数据库或既有设计/接口文档，不将方案写成已交付能力。按用户明确要求，后续先实施并阶段验收，实施完成后再依据最终行为同步 S01/S02、A04/A05/A06、B/F 等设计与说明文档；不沿用上一版“实施前先改既有设计”的步骤。

**现状核对**：当前任务最多三层，但父任务的状态/进度独立维护。项目当前对所有未删除、未取消任务平铺取平均，并非只计算一级任务，因此父子任务可能同时计入；本方案会改变这一口径。项目状态存库且默认未开始，尚未随任务联动；无任务项目没有手工进度字段/编辑能力。

**已确认的目标规则**：

| 节点 | 状态/进度来源 | 状态/进度编辑 |
| --- | --- | --- |
| 无未删除任务的项目 | 项目本身手工值，需补持久化和编辑入口 | 可编辑，遵守管理权限、版本校验与归档只读 |
| 无未删除子任务的任务（任意层级） | 本任务手工值 | 可编辑，保持现有“仅改百分比推导状态、显式状态优先”的叶子规则 |
| 有未删除子任务的任务 | 直接下级有效任务的汇总结果，再向本节点的上级传递 | 不允许直接修改普通状态或进度，服务端也必须拒绝绕过前端的写入 |
| 有未删除任务的项目 | 仅汇总一级任务的结果，不再次计入二/三级任务 | 不允许直接修改普通状态或进度 |

- 每层直接下级等权，保持层级权重，不改成所有叶子等权。例如一级 A 的两个子任务为 0%/100%，一级 B 为 100%，则 A 为 50%，项目为 (50%+100%)/2=75%，不是三个叶子平均约 67%。只有一项下级时继承其进度；最多三层任务的限制保持不变。
- 内部汇总保留足够精度，只在展示边界取整，避免逐层整数取整扩大误差。项目/父任务的状态依据下级实际状态及进度判断，不能用显示为 0% 或 100% 的整数认定未开始/已完成。全部有效下级完成才完成，任一下级实际已推进则至少进行中；显式状态与进度冲突的保守规则列入边界确认。
- 叶子进度与状态联动、逾期按日期派生的规则保持；不增加按开始日自动开工、按结束日自动完成，也不让百分比随时间增长。
- “是否有下级”按未删除结构关系判断，不以当前分页、筛选、可见列表或是否取消判断。取消任务不计入有效进度；仅有取消子任务仍不能把父节点当成可编辑叶子。取消分支、全取消时向上的传递方式在下方单列，不能按空集合自动完成。
- 父级只限制状态/进度两个业务字段，其余资料、成员、日期等仍按原权限和约束管理。不能因为用户能改某个叶子，就授予其编辑祖先资料的权限；祖先结果由系统汇总。

**实施前在本计划内明确的边界，不预先改既有设计**：

1. 暂停、取消、归档：严格的“非叶子状态不可手改”与原计划的父级人工覆盖存在冲突，原人工覆盖不再视为已确认规则。归档是否独立保留为管理操作、父级是否允许整分支暂停/取消，需先区分清楚；如保留，应明确为管理例外及恢复语义，不能作为普通状态编辑入口偷偷覆盖汇总。
2. 全部下级取消：是否将父节点派生为取消，以及该分支如何从上一层权重中排除；没有有效贡献时展示什么状态。无论最终选择哪种，都不得自动按“全部完成”处理，也不得开放父级手工进度。
3. 首末下级切换：添加第一项下级后进入汇总；删除/移走最后一项下级后恢复手工。旧手工值独立保留还是承接最后汇总值，仍需明确，界面必须说明；不静默恢复过时值。逻辑删除不参与汇总，恢复后重新计入。
4. 历史值与权限：旧父任务手工值不能继续与子任务重复计入。汇总以完整、经权限规则确定的任务树为基础，不依据当前页或筛选结果重算；父可见、子不可见时明确聚合信息边界，不返回隐藏子任务资料。旧数据迁移、必要的手工基线及撤回方案随实现评估。

**2026-10-27 实施边界确认**（本轮实施记录；最终设计文档同步按用户要求另行安排）：

- 归档保留独立管理操作，可解除归档并恢复树汇总。非叶子节点没有手工暂停、取消或进度覆盖；无任务项目保留手工暂停/取消。叶子显式状态优先，汇总仅在所有有效下级状态已完成且实际进度均为 100% 时判定完成，否则保守判定进行中。
- 全部直接下级取消时派生取消、进度为 0%，从上一层有效权重中排除；结构仍然存在，父级不能手工维护。
- 添加首个下级即采用汇总，删除/移走最后下级后承接最后一次汇总的展示值恢复手工，界面明确提示。删除父任务不删除其子任务；其仍存活子任务作为有效根参与项目汇总，恢复父任务后重新归入分支。
- 选择事务内持久化统一结果，使用 PostgreSQL numeric 保存中间精度，项目锁先于任务锁；任务状态筛选、排序、分页及提醒读取持久化有效值。完整任务树参与聚合，任何视图筛选不改变父级或项目结果；仅返回原权限允许的任务资料。计划总览按项目结果等权汇总，任务数量、逾期数量仍按视图内任务统计。
- 新迁移 000010 保存迁移前任务手工状态/进度及项目状态快照，并执行历史数据回填。回退需停写；down 恢复快照中既有对象的原手工值，因此会覆盖这些对象迁移后发生的状态/进度修改，回退前必须备份。新增对象保留回退时有效值。无任务项目新增持久化进度与编辑入口。

**动作先行的实施阶段与验收**：

1. **业务内核与数据准备**：在本计划补齐边界决策后，建立后端统一的树汇总逻辑，覆盖叶子、三层、直接下级权重、取消/删除、精度与状态。评估无任务项目手工进度、原手工基线及迁移；优先比较统一读取派生与受控持久化两种方案，GET 不写库，不分散到各前端页面各算一套。通过领域及真实依赖测试后提交阶段成果。
2. **查询与写入贯通**：项目/任务列表、详情、个人/组内计划、甘特图、状态筛选/排序、逾期统计与提醒统一使用最终结果；筛选计数和分页顺序不能失真。禁止非叶子状态/进度写入，与创建下级、手工保存并发时在事务内保证结构判定有效；修改子任务、取消、删除/恢复、同项目改父级时，原/新祖先链及项目都应反映最新结果。当前同项目父子约束保持，不扩展跨项目移动能力。验收后提交。
3. **前端接入与操作验收**：补无任务项目状态/进度编辑；非叶子显示汇总值、只读控件及来源说明，不能只用前端按钮禁用代替服务端校验。普通状态与管理例外分别呈现。验证三层变化、无下级/有下级切换、权限失效、并发和所有页面的一致性，再提交。
