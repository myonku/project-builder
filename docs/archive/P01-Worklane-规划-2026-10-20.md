## 3. Mongo 替换附件对象存储（W3）

> **W3 已落地（2026-10-21）**：`storage.backend=gridfs`、`cmd/storage-migrate`、
> 迁移 `000007` 与 `/health/ready` 的 Mongo 检查已完成；`local` 仍是默认。
> 旧数据需人工执行 copy → verify 后切换，详见 §3.5–§3.6。

### 3.1 现状

- `storage.Store` 只有 `Put/Open/Delete/Exists` 四个按 key 操作的方法；
- 本地实现 `storage.Local`，根目录 `storage.local_root`（默认 `./data/uploads`）；
- 附件元数据、配额、权限、审计都在 PostgreSQL；`stored_key` 形如 `attachments/<前两位>/<uuid>`，且**不由用户文件名派生**；
- `cmd/api` 与 `internal/testsupport/harness.go` 都直接 `storage.NewLocal(...)`；
- 配置校验目前只接受 `storage.backend=local`；备份文档只备份 PG + 本地附件目录。

### 3.2 决策建议

**MongoDB 只做字节存储（GridFS），PostgreSQL 仍是唯一业务事实源。**

- 不把附件元数据、权限、审计搬进 Mongo；否则会出现两套事务边界与两套权限判定；
- 保留 `storage.Store` 四方法接口，新增 `storage.GridFS`，业务模块（attachments/users）不改调用方式；
- 继续使用现有 `stored_key` 作为 GridFS 的 `filename`，**数据库里的 key 一字不改**；
- **附件与头像使用两个独立 bucket**（建议 `attachments`、`avatars`）：便于备份、生命周期与测试清理，也避免与附件 key 命名空间耦合；
- 附件 key 不可变；头像每次上传使用新 key，不做覆盖写。

### 3.3 依赖与实现点

| 层 | 改动 |
| --- | --- |
| 依赖 | `go.mongodb.org/mongo-driver/v2`（已为 **v2.5.0 direct**） |
| 平台层 | `internal/platform/mongo.go`（连接、Ping、Close）与 `internal/platform/storage/gridfs.go`（实现 `storage.Store`） |
| GridFS | bucket 由配置指定（附件 `attachments`、头像 `avatars`）；key 同时作为 fileID/filename，`Put` 先删旧再上传，`Open/Delete/Exists` 按 key；不依赖同名 revision |
| key 校验 | 把 `Local.resolve` 的路径安全检查抽成共享 `validateKey(key)`；GridFS 虽无目录穿越风险，仍复用同一套 key 不变式与测试 |
| 索引 | **不要给 `fs.files.filename` 建唯一索引**：GridFS 允许多 revision；`attachments.stored_key` 的唯一性由 PG 保证。建非唯一 `{filename:1, uploadDate:-1}` 索引即可 |
| 装配 | `cmd/api` 使用 `storage.NewFromConfig(...)`；按 `backend=local|gridfs` 选择；头像用同一 Mongo 客户端的 `avatars` bucket。集成测试 harness 仍用 local，GridFS 由 storage 包单独测试 |
| 健康 | `httpapi.Health` 增加 `MongoPing`；`/health/ready` 在 gridfs backend 下检查，错误 `object_storage_unavailable` |
| 关闭 | `platform.Mongo.Close()` 在 main 的 defer 中执行；Mongo 不可达时启动快速失败（附件是核心能力） |

### 3.4 配置建议

```toml
[storage]
backend = "local"                 # local | gridfs；迁移期保持 local，验证后切 gridfs
local_root = "./data/uploads"     # local 回退/迁移源
max_file_size = 10485760
max_files_per_user = 1000
allowed_extensions = [".pdf", ".png", ".jpg", ".jpeg", ".zip"]
gridfs_bucket = "attachments"     # 附件 bucket
avatar_bucket = "avatars"         # 头像 bucket
avatar_max_file_size = 2097152    # 2 MiB；不计入附件配额

[mongo]
uri = "mongodb://127.0.0.1:27017"
database = "worklane"
connect_timeout_seconds = 10
server_selection_timeout_seconds = 5
max_pool_size = 20
```

环境变量：`STORAGE_BACKEND`、`STORAGE_GRIDFS_BUCKET`、`STORAGE_AVATAR_BUCKET`、`STORAGE_AVATAR_MAX_FILE_SIZE`、`MONGO_URI`、`MONGO_DATABASE`、`MONGO_CONNECT_TIMEOUT_SECONDS`、`MONGO_SERVER_SELECTION_TIMEOUT_SECONDS`、`MONGO_MAX_POOL_SIZE`；`STORAGE_LOCAL_ROOT` 保留。`MONGO_URI` 可能含凭据，只能用环境变量注入，日志必须脱敏。

**默认值策略**：

1. 第 2 批落地后 `config.toml` 仍为 `local`，保证现有开发环境启动；
2. `docker/compose.test.yml` 增加 `mongo:9.0.4`（测试端口 27018），测试配置显式用 `gridfs` 跑附件集成测试；
3. 生产/试运行完成迁移并验收后，再把生产配置切为 `gridfs`；
4. `local` 保留为**迁移源与回退路径**，不删除实现；不实现“双写”。

### 3.5 旧数据迁移与回退

新增迁移 `000007_attachments_storage_backend`：给 `attachments` 加
`storage_backend VARCHAR(16) NOT NULL DEFAULT 'local'` + CHECK(`local|gridfs`) + 索引。
它只是**迁移账本**（每一行的字节当前在哪个后端），**不用于读路由**；服务始终只使用
当前配置的 `storage.Store`，避免引入“双读/混合读”而掩盖对象缺失。

新增 `cmd/storage-migrate`（不要塞进 `cmd/migrate`；schema 与数据迁移分离）：

```
storage-migrate copy   --from local --to gridfs --batch 100 --dry-run
storage-migrate verify --from local --to gridfs
storage-migrate status
storage-migrate rollback --from gridfs --to local
```

1. 读 PostgreSQL `attachments`（含已逻辑删除行）的 `stored_key`、`size_bytes`、`storage_backend`；
2. 从 `storage.local_root/<stored_key>` 读取字节，写入 GridFS 的相同 filename；
3. 校验：对象存在、字节数一致、SHA-256 一致（本地计算 vs GridFS 下载复核）；
4. 成功后把该行 `storage_backend` 更新为 `gridfs`；校验失败则该行保持 `local` 并停止；
5. 幂等：已存在且校验一致则跳过；大小不一致则报错并停止；`--dry-run` 只报告；
6. 不更新 `stored_key`，因此回退时本地仍能按同一 key 找到对象；
7. 迁移报告写入 stdout/可选 JSON：总数、成功、跳过、失败、总字节。

**切换步骤**：

1. 停写（或短暂维护窗口）；2. 跑迁移与校验；3. 切 `storage.backend=gridfs`；4. 重启；5. 抽查下载/彻底删除/配额；6. 保留本地目录至少一个发布周期；7. 验收后删除本地字节。

**回退**：不能只切配置——切换后新上传的附件只在 GridFS。`storage-migrate rollback` 必须
把 `storage_backend='gridfs'` 的所有行（含切换后新增）从 GridFS 反向复制回本地、校验，
再把行标回 `local` 后才能切回。回退前需确认本地容量能容纳新增字节。

**孤儿**：本地目录中无 DB 行引用的文件不复制，只报告；迁移不自动删除任何本地文件。
最终清理必须单独命令并人工确认。

### 3.6 备份与运维

- 备份对象从“PG + 本地附件目录”改为“PG + Mongo（`attachments`/`avatars` 两 bucket 的 `fs.files`/`fs.chunks`）”；两者必须同一备份批次；
- 恢复顺序：**Mongo 先、PG 后**（避免先出现指向空洞的行），应用在两者恢复完成前保持停止；恢复后按附件行数/总字节、`fs.files` 文档数/`sum(length)` 与抽样 SHA-256 对账；
- Mongo 不计入业务表迁移 head；但应在 B03 部署清单增加 `STORAGE_BACKEND=gridfs`、Mongo 连通性与 `mongodump/mongorestore` 验证；运行中做 `mongodump` 可能抓到不一致的 chunks，应停写/快照，或在副本集上使用 oplog；
- 过期/孤儿对象：先保持“以 PG 行为准”，迁移/清理脚本仅报告不自动删除。

| 测试 | 内容 |
| --- | --- |
| 存储契约 | `Put/Open/Delete/Exists` 对 local 与 gridfs 各跑一套；缺失对象返回 `ErrObjectNotFound`，重复删除幂等 |
| 附件集成 | 上传 → 下载字节比对 → 逻辑删除 → 彻底删除；配额、审计不变 |
| 迁移工具 | 临时本地目录 + 临时 GridFS：正常复制、跳过已存在、大小不一致报错、幂等重跑、反向回滚 |
| 健康检查 | gridfs backend 下 Mongo 关闭返回 `503 object_storage_unavailable` |
| 回滚 | 切回 local 后旧附件仍可下载/彻底删除 |
| 回归 | `go test ./... -count=1 -p 1`；附件冒烟 207 项中的附件段通过 |

**风险**：多一个数据存储（备份/恢复/监控复杂度上升）；GridFS 不适合超大文件；本地回退期磁盘占用翻倍；Mongo 与 PG 的“行/对象”一致性仍需靠应用层顺序（先写对象后写行、彻底删除先删对象再删行）。

## 4. 头像与 `/me` 个人信息页（W2 + W4）

### 4.2 数据模型建议

在 `users` 表增加 **4 个可空/派生列**（迁移 `000008`）：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `avatar_stored_key` | VARCHAR(512) | NULL，UNIQUE（部分索引） | 存储 key；**永不返回客户端** |
| `avatar_mime` | VARCHAR(160) | NOT NULL DEFAULT '' | 服务时使用的 Content-Type |
| `avatar_size_bytes` | BIGINT | NOT NULL DEFAULT 0，CHECK ≥0 | 头像大小，不计入附件配额 |
| `avatar_updated_at` | TIMESTAMPTZ | NULL | 对外只暴露这个字段，用于缓存失效 |

**不变式**：`avatar_stored_key` 与 `avatar_updated_at` 同时为空或同时非空；头像更新**不推进** `users.updated_at`（避免个人资料表单因上传头像产生 409），只推进 `avatar_updated_at`。头像更新/删除写 `user/updated` 审计，`changes` 只记 `avatar=set|cleared`，不记 key/内容。

### 4.3 存储与 key

- 使用 W3 的同一个 `storage.Store`（Mongo 或 local），key 形如 `avatars/<user_uuid>/<uuid>`；
- 每次上传写新 key，更新 DB 成功后再删除旧对象；DB 失败则删除新对象；
- 删除头像：DB 置空成功后才删对象；对象删除失败只记录告警（行已失效，不会继续展示）；
- 头像**不计入** `storage.max_files_per_user`；单独 `storage.avatar_max_file_size`（建议 2 MiB）与固定尺寸上限 4096×4096。

## 5. 邮箱验证重置密码（W5）

### 5.1 实施前基线与已确认语义

- 现有只有管理员 `POST /users/{id}/password`；登录页“忘记密码”是占位提示；
- 没有邮箱验证令牌表、没有自助重置端点、没有邮件模板；
- 当前管理员重置**不吊销**会话（B05 7.3 #5）；自助重置必须让旧会话失效。

**需求语义建议固定为**：

1. **成功重置冷却 7 天**：同一用户两次成功自助重置至少间隔 7×24 小时；
2. **滚动 7 天内最多 5 次验证邮件请求**：请求成功/失败/过期/撤销都计数；第 6 次起不再发送；
3. 冷却期内请求仍返回统一的“已受理”，但不发邮件（避免暴露账号状态）；
4. 仅在用户 `status=active` 且有邮箱时发送；不存在/停用/无邮箱一律返回同一 202，不泄漏；
5. 令牌 30 分钟有效、单次使用；新请求撤销旧令牌；
6. 重置成功后吊销该用户全部既有会话，必须重新登录。

### 5.2 数据模型（迁移 `000009`）

**`password_reset_states`（每用户一行）**：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK（不能只用 user_id 当 PK；全局约定要求业务表有 id/created_at/updated_at） |
| `user_id` | UUID | NOT NULL，UNIQUE，FK → `users(id)` ON DELETE CASCADE |
| `last_self_service_reset_at` | TIMESTAMPTZ | NULL；只由自助成功写，管理员重置不写 |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |

**`password_reset_tokens`（每次签发一行）**：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK |
| `user_id` | UUID | NOT NULL，FK → `users(id)` ON DELETE CASCADE |
| `token_hash` | VARCHAR(64) | NOT NULL，UNIQUE（SHA-256 hex；**不存原始 token**） |
| `requested_at` | TIMESTAMPTZ | NOT NULL；滚动计数与 TTL 的基准，使用注入时钟 |
| `expires_at` | TIMESTAMPTZ | NOT NULL，CHECK > `requested_at` |
| `consumed_at` | TIMESTAMPTZ | NULL；成功/被新请求作废/管理员重置或邮箱变更/停用时写入 |
| `sent_at` | TIMESTAMPTZ | NULL |
| `failed_at` | TIMESTAMPTZ | NULL |
| `last_error` | VARCHAR(500) | NULL，截断后的 SMTP 错误；**不得包含 token**，按 PII 处理 |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |

索引/约束：
- `uq_password_reset_tokens_token_hash`；
- `ix_password_reset_tokens_user_requested (user_id, requested_at DESC)`；
- 推荐 `uq_password_reset_tokens_active_user ON (user_id) WHERE consumed_at IS NULL`，把“一用户只有一个有效链接”变成数据库不变式。

`users` 增加 `session_version INTEGER NOT NULL DEFAULT 0`（同一迁移 `000009`）：

- 登录成功时把当前 `session_version` 写入 Redis 会话；
- 每次会话解析时与数据库当前值比较，不一致即视为会话失效；
- 自助重置成功、管理员重置成功后 `session_version++`；
- 平滑兼容：旧会话 JSON 没有该字段时按 0 处理；用户初始值 0，因此升级后不会误踢。

> **为什么不用扫描 Redis 删除所有会话**：会话版本是单点判定，跨重启/多实例都成立；
> 逐 key 扫描在大规模会话下不可控，也容易漏掉。版本比较由已有的 `CurrentUser` 读取路径完成。
> **锁顺序固定为 users → password_reset_tokens**，避免与管理重置并发时死锁。

### 5.3 接口（已落地）

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/password-reset/request` | 公开 | 请求体 `{email}`；统一 202（无论账号是否存在/是否限流） |
| `POST` | `/api/v1/auth/password-reset/confirm` | 公开 | 请求体 `{token, new_password}`；成功 204；无效/过期/已用/冷却/停用统一 422 `password_reset_token_invalid` |

两个端点加入会话网关白名单的**精确路径**（不要加 `/auth/password-reset` 前缀，避免未来子路径意外公开）。

**请求流程**：

1. 校验 email 格式（`NormalizeEmail`）；`password_reset_enabled=false` 或 `mail.enabled=false` 时，在查库前返回 `503 password_reset_unavailable`（对所有邮箱一致，不构成枚举）；
2. `FindByEmail`（**不要用 `FindByIdentifier`**：用户名可能与另一个人的邮箱相同）；不存在/停用/无邮箱 → 直接 202；
3. 事务内锁 users 行；读/建 `password_reset_states`；若 `last_self_service_reset_at + cooldown > now` → 提交后 202，不发信；
4. 统计最近 `window` 内的 token 行；≥5 → 提交后 202，不发信（冷却/配额内请求不建 token，因此不重复计数）；
5. 否则把该用户所有 `consumed_at IS NULL` 的旧 token 置为当前时间（最新链接生效），生成 32 字节随机 token、保存 SHA-256，插入新 token 行；
6. 提交后发送邮件（独立 10–15s 超时）；成功/失败更新 `sent_at`/`failed_at`/`last_error`，仍返回 202（发送失败不暴露账号存在性）；
7. 202 响应体建议 `{"data":{"status":"accepted"}}`；新增 `httpapi.RespondAccepted`。

**确认流程**：

1. 校验 token 形状（64 hex）与新密码（复用 `NormalizeNewPassword`，422 带 `fields.new_password`）；强度失败不消费 token；
2. 按 token_hash 做**非锁定**查询拿 `user_id`；不存在直接 422，避免对无效 token 做 Argon2（CPU DoS）；
3. 在事务外计算 Argon2 摘要（约百毫秒），避免持锁做 CPU 重活；
4. 事务内锁 users 行 → 校验状态/邮箱 → 读 state 冷却 → `UPDATE password_reset_tokens SET consumed_at=$now WHERE token_hash=$1 AND consumed_at IS NULL AND expires_at > $now RETURNING user_id`（0 行即 422）；
5. 更新密码摘要 + `session_version++` + 标记该 token 已消费 + 消费该用户所有未消费 token + 更新 state `last_self_service_reset_at` + 写 `user/password_reset` 审计（同事务）；
6. 提交后返回 204；用户用新密码登录。**不自动登录**；旧会话因 `session_version` 不匹配而 401。

**错误码**：

| 状态 | code | 触发 |
| --- | --- | --- |
| 202 | — | 请求已受理（存在/不存在/停用/冷却/超 5 次均同形） |
| 204 | — | 确认成功 |
| 422 | `validation_error` | email/token 形状、new_password 强度 / 未知字段 |
| 422 | `password_reset_token_invalid` | token 不存在/过期/已用/被撤销、冷却中、用户停用/无邮箱 |
| 429 | `rate_limited` | 仅 IP 级限流，带 `Retry-After` |
| 503 | `password_reset_unavailable` | 功能关闭或邮件未启用（查库前） |

请求端点**不返回 404/409**，账号级配额只用 202 表达，避免枚举。

### 5.4 邮件与配置

- 复用 `mail.Sender`；纯文本邮件，主题 `Worklane 密码重置`；
- 正文含显示名、有效期分钟数、链接、“如非本人操作请忽略”；**绝不含新密码**；
- 正文含链接：`{password_reset_url_template}`，占位 `{token}`；链接由前端域名决定，必须配置；
- 邮件只指向**前端页面**（GET 不消费 token），确认必须由页面发 POST；这样邮件客户端/安全网关的链接预取不会消耗 token；
- 建议配置：

```toml
[mail]
password_reset_url_template = "http://localhost:5173/reset-password?token={token}"

[security]
password_reset_enabled = true            # 有效可用还要求 mail.enabled
password_reset_token_ttl_seconds = 1800  # 30 分钟
password_reset_cooldown_seconds = 604800 # 7 天
password_reset_window_seconds = 604800   # 滚动 7 天
password_reset_max_requests = 5
password_reset_ip_requests_per_hour = 10 # 0=关闭；防邮件轰炸
```

- `password_reset_enabled=false` 时 request/confirm 都返回 503 `password_reset_unavailable`；
- `mail.enabled=false` 时 request 返回 503；**confirm 仍允许**，避免已发出的链接在邮件关闭后突然失效；
- 生产必须 `mail.enabled=true`；测试用 Mailpit/fake sender 捕获 token；
- `cmd/api/main.go` 当前在 auth 之后构造 mail，落地时必须把 mail 段上移再注入 auth；`testsupport` 同样调整。

### 5.6 安全与审计

- 原始 token 只出现在邮件链接与客户端内存；数据库仅存 SHA-256；
- 请求端点统一 202，避免邮箱枚举；错误信息不区分“账号不存在/停用/已限流”；
- 令牌单次、30 分钟、撤销旧令牌；确认失败不泄漏用户是否存在；
- 审计：`password_reset`，actor=本人，object=user，`changes={"source":"self_service"}`；**不记 token/密码/摘要**；
- 全局限流之外，业务层 7 天/5 次是硬限制；request 另挂按 IP 的桶（默认 10/小时，0 关闭），
  防止“批量给不同账号发重置邮件”的邮件轰炸；IP 限流返回 429，不作为账号存在性信号；
- 旧会话失效由 `session_version` 保证；管理员重置也应递增（修正 B05 7.3 #5 的“不吊销”决策）；
- **管理员重置、邮箱变更、停用账号**都必须消费该用户未使用的自助 token（锁顺序 users → tokens），
  否则旧邮件链接可以在这些安全操作之后继续改密码；
- **计时侧信道**：同步 SMTP 实测约 700ms，未知邮箱几乎立即返回。MVP 接受该差异
  （由全局限流 + IP 桶 + 内部网络缓解），并在 B04 登记；若要彻底消除，需要异步发送/出站表，
  复杂度明显更高，不放在初版；
- **发送失败仍计入 5 次**：SMTP 故障会暂时消耗用户配额，运维可清理 token 行；
  请求端点仍返回 202，不能因发送失败对“存在的邮箱”返回 5xx（否则就是枚举通道）。

### 5.7 测试与验收

- 请求：存在/不存在/停用/无邮箱/冷却/第 6 次/邮件失败/邮件未启用；并发 10 个请求只签发最多 5 个 token；
- 令牌：过期、已用、撤销、错误 token、并发确认、最新链接生效（旧链接失效）；
- 成功：旧密码不能登录、新密码能登录、旧会话 401、审计记录无敏感值；
- 限流：滚动 7 天内 5 次后第 6 次不发信；成功重置后 7 天内不再发；推进注入时钟 7 天后恢复；
- 管理端：管理员重置也 `session_version++`；管理员重置/邮箱变更/停用会消费未使用 token；
- 迁移：head 8→9、表数、`password_reset_states` 有完整审计列、外键 CASCADE、down 可回退；
- 前端：提交/错误/成功/密码强度/两次不一致/链接失效；token 从 URL 读取后立即从历史中移除；
- 安全：数据库/日志/审计中不出现原始 token、密码或完整邮箱链接；无效 token 不做 Argon2。
