## 1. 检查结论

**普通用户缺少新建入口的判断成立，但“只有管理员能创建”只适用于当前前端。后端实际上允许任意登录用户直接创建工作组，当前需求和接口文档也明确如此规定。** 因此本阶段需要同时解决入口缺失和直接创建绕过审核两个问题。

## 2. 目标与首期范围

目标流程：有效登录用户提交名称、说明和申请理由 → 系统管理员查看与审核 → 通过后才产生可用组，申请人成为所有者及活跃组管理员 → 申请人从本人记录进入工作组。

首期包含：

- 普通用户自助申请、本人记录与详情、状态筛选、拒绝原因展示、被拒后复制内容重新提交。
- 系统管理员全局待审及历史记录、查看详情、通过或拒绝；继续支持管理员直接创建。
- 独立创建申请表、原子审核建组、并发和重复提交保护、同事务审计、权限收口。
- 桌面与手机布局、空列表引导、失败保留输入、提交结果不确定时的核对路径。

首期不安排草稿、提交后修改/撤回、批量审批、多级审核、指定他人为首任所有者、自动批准、邮件通知或新建消息中心。状态先采用 pending/approved/rejected 三种；需要撤回时另增状态与接口，不用 rejected 代替用户撤回。

以下作为建议实施默认值，后续产品调整应先改本文：申请理由必填；拒绝理由必填；同一申请人同名仅允许一条待审记录；不同名称可分别申请；管理员直接建组仍以本人为所有者。管理员提交申请时与普通申请走相同流程，也可由系统管理员本人审核；本阶段不新增双人审批要求。

## 3. 页面与交互

### 3.1 工作组 `/groups`

- 页头新增主操作“申请新建工作组”，与“刷新”并列；无已加入组时显示说明及同一申请入口，避免新用户无处开始。
- 将原“我的申请”改名为“加入申请”，保留现有搜索、加入记录和审核能力；增加“新建申请”页签，避免把两种申请混成一份列表。
- 新建弹窗包含：工作组名称（必填、去首尾空白、1–160 Unicode 码点）、说明（选填、最多 2000 码点）、申请理由（必填、去首尾空白、1–2000 码点）。显示“系统管理员审核通过后创建，你将成为所有者”。不提供所有者、角色、组状态、申请状态输入。
- 提交后显示“新建申请已提交”，切至“新建申请”并刷新记录；待审期间不显示为“我的组”，不生成可进入的 groupId。
- 本人列表展示申请时名称、状态、提交时间、审核时间和操作；详情展示说明、理由、拒绝原因。通过后提供“进入工作组”，拒绝后提供“重新申请”，复制原内容至新表单并生成新记录，不覆盖历史。
- 申请时内容是不可变快照；通过后当前组名、组状态另行展示。工作组后来停用、改名、转移所有权或申请人被移出时，历史审批结果保持原值，访问能力重新按当前组权限判断。

### 3.2 组管理 `/admin/groups`

- 增加“工作组 / 新建申请”页签；既有列表、详情抽屉和直接“新建工作组”保持原功能，按钮明确为“直接新建工作组”。新页签标题为“新建申请审核”，不是让管理员代填用户申请。
- 申请页签默认筛选待审核，支持全部/待审核/已通过/已拒绝、名称或申请人查询、服务端分页与排序；筛选变化回到第一页。待审数量从服务端真实总数获得，不统计当前页。
- 列表展示名称、申请人姓名/用户名、提交时间、状态、审核时间；详情完整展示申请内容、申请人当前账号状态及审核记录。
- “通过”先确认名称和申请人成为所有者；“拒绝”要求填写原因。审核不顺便修改申请内容、替换所有者或把申请附着到已有组；内容不合适则拒绝后重新提交。
- 并发冲突后读取最新详情并更新列表；响应丢失时提示核对结果，不能连续调用直接创建补救。通过后可打开新组详情。

### 3.3 共用约束

复用现有 MUI 弹窗、状态标签、时区格式化、`useListQuery` 和字段错误展示；名称/说明字段校验可从 `GroupFormDialog` 提取，共享字段而不混用“直接创建”和“提交申请”的成功语义。前端长度校验应与服务端 Unicode 码点口径一致。

手机端操作区可换行，详情适配窄屏；提交中禁止重复点击，失败保留表单。本人列表与管理员列表独立维护分页/筛选，账号切换时清空缓存；只有对应页签启用查询，防止隐藏页签持续请求。

## 4. 权限与生命周期

| 能力 | 有效登录用户 | 组所有者 / 组管理员 | 系统管理员 |
| --- | --- | --- | --- |
| 提交创建申请、查询本人记录 | 允许 | 同普通用户 | 允许 |
| 查看某条申请 | 仅本人 | 仅本人，不因组角色扩权 | 全部 |
| 查询全局创建申请、审核 | 禁止 | 禁止 | 允许 |
| 直接 `POST /groups` | **改为禁止** | **改为禁止** | 保留 |
| 审核已有组的加入申请 | 沿用现行权限 | 沿用现行权限 | 沿用现行权限 |

停用账号不得提交；审批通过时在事务中重新检查申请人仍为有效账号。若已停用，保留 pending，返回业务冲突，管理员可拒绝并说明原因；不创建归属停用用户的组。审核者资格也必须依据当前账号状态和系统角色，不能相信前端或客户端传入的 reviewer_id。

状态转换只有 `pending → approved` 或 `pending → rejected`。终态记录不可修改或回到 pending；重新申请产生新 id，完整保存每轮内容和结论。与现有加入申请“每组每用户只保存最新状态”的规则不同。

审核前不存在真实组，因此不会进入目录、成员关系、项目归属或计划统计。通过后创建 `groups.status=active`，`owner_id=applicant_id`，并创建 `group_members(role=manager,status=active)`。审核者不会自动成为所有者或成员。

## 5. 数据模型与迁移建议

拟新增 `group_creation_requests`，使用 PostgreSQL 和现有 UUID 生成器，不新增服务依赖。

| 字段 | 类型/约束 | 含义 |
| --- | --- | --- |
| id | UUID PK | 申请 id |
| created_at / updated_at | TIMESTAMPTZ NOT NULL | 提交时间及版本；应用显式更新 updated_at |
| applicant_id | UUID NOT NULL，FK users，ON DELETE RESTRICT | 申请人，由会话取得 |
| name | VARCHAR(160) NOT NULL | 已清洗的申请名称快照 |
| description | VARCHAR(2000) NULL | 说明快照；空白归一为 null |
| reason | VARCHAR(2000) NOT NULL | 申请理由，禁止空白 |
| status | VARCHAR(16) NOT NULL DEFAULT pending | pending / approved / rejected |
| reviewed_by | UUID NULL，FK users，ON DELETE RESTRICT | 审核者 |
| reviewed_at | TIMESTAMPTZ NULL | 审核时间 |
| rejection_reason | VARCHAR(2000) NULL | 拒绝时必填、禁止空白 |
| group_id | UUID NULL，FK groups，ON DELETE RESTRICT | 通过后产生的组 |

数据库约束与索引：

1. CHECK 状态白名单和字段一致性：pending 的审核人、时间、拒绝原因、group_id 均为 null；approved 必须有审核人、时间、group_id，拒绝原因为 null；rejected 必须有审核人、时间、非空拒绝原因，group_id 为 null。名称和理由增加非空白约束。
2. `group_id` 非空时唯一，一个新组只能对应一条通过记录；应用保证 approved 对应组及首任所有者成员关系同事务产生，后续合法所有权转移不改申请快照。
3. 部分唯一索引 `(applicant_id, lower(name)) WHERE status='pending'`，name 先沿用领域层 Unicode 去首尾空白规则；查询重复使用相同数据库表达式，不自行用另一套大小写算法。拒绝后可新提交，历史行保留。
4. 查询索引 `(applicant_id, created_at DESC, id)`、`(status, created_at, id)`；`q` 初期按字面子串查询申请名称或申请人用户名/显示名，参数化 SQL，真实数据量下检查执行计划后再决定文本索引。

**不引入工作组全局同名唯一约束。** 现有组可同名，同名申请可能来自不同用户，管理员结合用途判断；已有组与其他待审记录可作为审核提示，但不能仅凭同名自动加入、复用或转移已有组。

预计下一迁移为 `000013_group_creation_requests`，实际实施前重新确认 head。只增新表及相关约束/索引、扩展审计白名单，不把现有工作组补造为已审核申请，不更改加入申请表。

## 6. 拟议接口与错误语义

基础路径均为 `/api/v1`，沿用 data/分页/错误信封、严格未知字段拒绝、会话认证和全局限流。以下新增 5 个端点，路径在 A03 定稿后实现；不将表中的规划数计入当前基线。

| 方法与路径 | 权限 | 请求与结果 |
| --- | --- | --- |
| `POST /group-creation-requests` | 有效登录用户 | `{name, description?, reason}`；必填 `Idempotency-Key`；新建 201，重放 200 |
| `POST /me/group-creation-requests/query` | 有效登录用户，仅本人 | `{status?, page?, page_size?, sort?}`；不接受 applicant_id |
| `POST /group-creation-requests/query` | 系统管理员 | `{status?, q?, applicant_id?, page?, page_size?, sort?}`；全局分页 |
| `GET /group-creation-requests/{request_id}` | 申请人本人或系统管理员 | 单条详情、updated_at、审核结果及可见的关联组信息 |
| `POST /group-creation-requests/{request_id}/review` | 系统管理员 | `{status: approved或rejected, rejection_reason?, expected_updated_at}`；成功 200 |

本人列表建议默认 `-created_at`，待审管理列表显式 `created_at` 升序，支持 created_at/updated_at/status 排序并追加 id；page/page_size 默认 1/20，最大 100。q 去首尾空白、最长 160 码点，按字面子串匹配，不将 `%`、`_` 或反斜杠解释为通配符。列表 total 与筛选条件一致。

通用响应包含申请 id、申请内容、status、created_at、updated_at、reviewed_at、rejection_reason、group_id；group_id 未通过为 null。本人的投影不包含其他申请人信息或审核者邮箱。管理员额外取得 applicant_id、username、display_name、账号状态及 reviewed_by；不逐行补查用户。关联组的当前详情/访问能力按现有鉴权处理，历史获批不赋予永久读组权限。

错误约定：未登录 401；全局查询、审核、原直接创建的非系统管理员 403 permission_denied；他人申请详情与不存在的申请统一 404 resource_not_found；非法 UUID/分页/排序为 400；缺字段、非法状态、长度、空白、未知字段、缺审核版本或幂等键为 422；已有同名 pending 申请、已终态审核、申请人已停用为 409 conflict；版本不匹配为 409 version_conflict。限流沿用 429 和 Retry-After。

通过不接受非空 rejection_reason；拒绝必须提供非空 rejection_reason；申请人、审核人、group_id、owner_id、成员角色与时间均由服务端生成。审核不能接受 pending。错误字段和检查顺序需在 A03 与测试中固定。

提交防重建议复用已有 `idempotency_keys` 表与 201/200 语义，作用域为 `(user_id, group_creation_requests.create, key)`，result_id 指向申请，键最长 200 字符、禁止空白。新表记录、幂等映射和审计在同一事务写入；唯一冲突不得留下孤立申请。相同 key 始终返回原申请的当前状态，即使原申请已终态也不新增；重新申请必须生成新 key。复用 key 不代表更新内容，客户端编辑为新一轮申请时必须换 key。不同 key 的同名 pending 提交由部分唯一索引返回 409。

## 7. 审核事务、审计与失败恢复

批准的一次事务应完成：

1. 在事务授权裁决点确认审核者有效且为系统管理员，锁定/检查申请人的有效账号状态及申请行；与账号停用/角色变更遵循统一锁顺序，实施前核对 users 模块，避免反向加锁。
2. 检查 pending 与 expected_updated_at，生成组及成员 id。并发审核按行锁/CAS 串行判定，不用事务外“先查 pending 再无条件写入”。
3. 插入组、申请人的活跃 manager 成员行，写入申请的 approved/group_id/reviewed_by/reviewed_at/updated_at，并写入审计。
4. 提交后回读权威申请；任一步失败全部回滚。拒绝只更新申请与审计，不产生组或成员。

现有 `CreateGroupInTx` 自己开启事务，不能在它提交之后才更新申请。建议提取接收同一事务 Querier 的底层建组函数，分别供管理员直接建组与申请审核复用；用例层区分 actor（执行审核的管理员）和 owner（申请人），不能沿用 CreateInput.OwnerID 同时代表操作人的假设。

审计建议新增对象 `group_creation_request` 和动作 `group_creation_reviewed`；提交记 created，审核记专用动作，批准另外记真实 group 的 created，actor 为审核者、changes 含 applicant_id/request_id/group_id/decision。申请理由及完整拒绝原因保存在申请表，审计只记录摘要或“已填写”事实，避免摘要截断影响追溯。

注意当前 `activity_logs.object_type` 是 VARCHAR(16)，新对象名超过 16 字符；同一迁移需扩为 VARCHAR(32)、修改数据库 CHECK，并同步 domain 枚举、审计 API 白名单、前端类型/标签/筛选及枚举一致性测试。新动作同样进入 CHECK 与两端白名单，不能只增加 Go 常量。

同一申请并发通过/拒绝只有一个成功；另一请求在终态下返回 409 并展示最终结果，不能再建组。审核响应丢失时按 request_id 读回；重发审核即使得到 409，也不会重复副作用。提交响应丢失则用原幂等键重放，不自动生成新 key。

## 8. 兼容、发布与回退
