# 配置与运行

## 1. 文档定位

本文档是运行配置、启动流程和迁移操作的权威来源，承接《01-Go服务端架构设计.md》第 7 节与
Python 版本的《项目计划管理系统-全局基线约定.md》第 7 节。接口行为见《04-HTTP接口契约.md》。

对应实现：`internal/config/config.go`、`cmd/api/main.go`、`cmd/migrate/main.go`。

## 2. 配置优先级

```text
代码默认值  <  config.toml  <  .env 文件  <  进程环境变量
```

- 代码默认值集中在 `internal/config/config.go` 的 `defaultConfig()`，全部可安全落到开发环境。
- `config.toml` 提供本地开发默认值；文件不存在**不算错误**（纯环境变量部署场景）。
- `.env` 用于本地覆盖；文件不存在同样不算错误。
- 进程环境变量优先级最高，用于生产与 CI。

实现要点：

- 空字符串的**进程环境变量**视为"未设置"，不会覆盖 `config.toml` 的值。
  这避免了 CI 中常见的 `DATABASE_HOST=` 把配置清空。
- `.env` 中的空字符串是**有意覆盖**（例如显式清空 `MAIL_PASSWORD`）。
- 新增配置项必须同时在 `envBindings()` 中登记，否则无法通过环境变量覆盖；
  `internal/config/config_test.go` 有唯一性断言防止重复登记。

### 3.5 存储

| TOML | 环境变量 | 默认值 |
| --- | --- | --- |
| `storage.backend` | `STORAGE_BACKEND` | `local`（仅支持 local） |
| `storage.local_root` | `STORAGE_LOCAL_ROOT` | `./data/uploads` |
| `storage.max_file_size` | `STORAGE_MAX_FILE_SIZE` | `10485760`（10 MiB） |
| `storage.max_files_per_user` | `STORAGE_MAX_FILES_PER_USER` | `1000` |
| `storage.allowed_extensions` | `STORAGE_ALLOWED_EXTENSIONS` | 空（不限制） |

**`max_files_per_user`**：单个账号最多关联的附件数量，**含已逻辑删除的**——
它们仍占磁盘，彻底删除才是回收点（见 docs/04 §4.8 的配额口径）。
单项目/任务不限制附件数量。

**`allowed_extensions`**：扩展名白名单，每项**必须含点号**（如 `.pdf`），
匹配忽略大小写。**空数组或 `["*"]` 表示不限制**；环境变量用逗号分隔，
留空即不限制。配置项在启动时校验（缺少点号会启动失败），
不匹配的上传返回 `415 unsupported_media_type`。

**关于这一层的设计**：对象存储被压到"按 key 做 CRUD"这四个方法
（`internal/platform/storage`），不含任何业务语义。初版只实现本地文件系统，
但真实数据里"文件"往往是最难迁移的部分，因此刻意留出这个边界：
将来换对象存储或基于 MongoDB 的实现时，只需再实现这四个方法，
数据库里的 `stored_key` 一字不改即可沿用。任何业务规则都不得下沉到那一层。

### 3.5.1 邮件（提醒的发送通道）

邮件**默认关闭**：打开它就必须同时提供账号与发件地址，否则"启动成功但每封都发不出去"
是最难排查的一种状态。因此启用邮件是一次显式动作。

| TOML | 环境变量 | 默认值 |
| --- | --- | --- |
| `mail.enabled` | `MAIL_ENABLED` | `false` |
| `mail.host` | `MAIL_HOST` | `smtp-mail.outlook.com` |
| `mail.port` | `MAIL_PORT` | `587` |
| `mail.username` / `mail.password` | `MAIL_USERNAME` / `MAIL_PASSWORD` | 空（**只从环境变量注入**） |
| `mail.from_address` / `mail.from_name` | `MAIL_FROM_ADDRESS` / `MAIL_FROM_NAME` | 空 / 项目计划管理系统 |
| `mail.use_tls` | `MAIL_USE_TLS` | `true`（明文连接上协商 STARTTLS，适配 587） |
| `mail.implicit_tls` | `MAIL_IMPLICIT_TLS` | `false`（直接 TLS，适配 465） |
| `mail.auth_method` | `MAIL_AUTH_METHOD` | `login` |
| `mail.oauth2_access_token` | `MAIL_OAUTH2_ACCESS_TOKEN` | 空（仅 `xoauth2` 用） |
| `mail.task_url_template` | `MAIL_TASK_URL_TEMPLATE` | `http://localhost:8080/tasks/{task_id}` |

`use_tls` 与 `implicit_tls` 必须分开：465 上"先明文再 STARTTLS"会直接失败，
587 上直接 TLS 也连不上；合成一个布尔量必然产生"配置看起来对、但永远连不上"的状态。

**认证机制（实测结论，2026-10-11）**：拿真实邮箱对 `smtp-mail.outlook.com:587`
实测得到三点：

1. **STARTTLS 可用**，会话能正常推进到认证阶段；
2. **服务器不接受 `AUTH PLAIN`**，回应 `504 5.7.4 Unrecognized authentication type`；
   `LOGIN` 与 `XOAUTH2` 都被接受（因此默认机制是 `login`，并在服务端明确表示
   不认识该机制时自动改用 `plain`）；
3. 用应用密码走 `LOGIN` 得到 `535 5.7.3 Authentication unsuccessful`——
   即**凭据被拒**（不是机制问题）。这与官方页面标注的"OAuth2/Modern Auth"一致：
   该邮箱要求 OAuth2，普通应用密码不被接受。

因此 `auth_method = xoauth2` 是为该场景准备的路径，但它需要一枚**外部获取的访问令牌**
（换取令牌所需的 client_id / tenant 由部署方持有；本服务不实现 OAuth2 授权码流程）。
若部署方希望继续用应用密码，需要在邮箱侧启用 SMTP AUTH（企业邮箱由管理员
在邮箱策略里打开"Authenticated SMTP"）。

**凭据绝不入库**：`config.toml` 已纳入版本控制，因此 `username` / `password` /
`oauth2_access_token` 一律留空，由环境变量或未入库的 `*.local.toml` 提供。

### 3.6.1 引导管理员（系统初始化）

| TOML | 环境变量 | 默认值 |
| --- | --- | --- |
| `security.bootstrap_admin_username` | `SECURITY_BOOTSTRAP_ADMIN_USERNAME` | 空（功能关闭） |
| `security.bootstrap_admin_email` | `SECURITY_BOOTSTRAP_ADMIN_EMAIL` | 空 |
| `security.bootstrap_admin_password` | `SECURITY_BOOTSTRAP_ADMIN_PASSWORD` | 空 |
| `security.bootstrap_admin_display_name` | `SECURITY_BOOTSTRAP_ADMIN_DISPLAY_NAME` | 空（回退为用户名） |

**为什么需要它**：本系统的使用场景中普通用户不需要管理员角色，因此**没有分发管理员的
需求**，只需要在系统初始化时录入**一个**系统级后台账号。而全部管理员端点都要求调用者
已是管理员，所以必须有一个不依赖 HTTP 的初始化入口——就是这组配置。

**语义**（实现见 `auth.Service.EnsureAdministrator`，在 `cmd/api` 启动过程中执行一次）：

| 情况 | 行为 |
| --- | --- |
| `bootstrap_admin_username` 为空 | 功能关闭，不做任何事 |
| 账号不存在 | 按给定的邮箱/密码/显示名创建，`status=active`、`system_role=admin` |
| 账号已存在且已是 admin | **什么都不做**（连 `updated_at` 都不推进，避免无谓地让客户端版本失效） |
| 账号已存在但不是 admin | 只把 `system_role` 改为 `admin` |
| 账号已存在但处于停用 | 只改角色并**告警**；不自动启用（自动启用会与一次显式的人工停用相抵触） |

两条必须遵守的性质：

1. **幂等**：初始化在每次启动时执行，重复执行不产生副作用。
2. **绝不覆盖既有账号的密码、邮箱与状态**。否则每次重启都会把管理员改过的密码打回
   配置里的初始值，而配置里的初始化密码通常早已从环境中移除——结果是所有人都进不去。
   这条性质由 `TestEnsureAdministratorPromotesExistingAccountWithoutTouchingPassword`
   与集成测试 `TestBootstrapAdministratorUnlocksAdminEndpoints` 锁住。

因此 `bootstrap_admin_password` 是**一次性**的：账号建好之后即可从环境中移除
（`config.toml` 与 `.env.example` 中该键默认被注释掉）。

**校验规则**：4 项要么整组配置、要么全部留空。只配一部分会导致**启动失败**
（例如只配用户名会让一次本该创建管理员的初始化静默地什么都不做，
而操作者以为自己已经录入完毕）。用户名/邮箱/密码的格式与强度由注册的归一化规则校验，
配置层不重复实现。

测试环境显式启用了这组配置（`docker/config.test.toml` 与 `Makefile` 的
`TEST_BOOTSTRAP_ADMIN_*`），使端到端冒烟能够覆盖管理员端点的**成功路径**。

## 4. 启动校验与快速失败

配置在启动时读取一次，解析、校验后成为不可变对象注入各模块。校验失败**立即退出**，
并输出脱敏后的字段名与原因。

校验覆盖：

- 端口范围、超时与连接池正数性、`min_conns <= max_conns`。
- 必填项非空（`database.name`、`database.user`、`session_secret`、`session_cookie_name`）。
- `password_min_length >= 8`。
- `storage.backend` 必须是 `local`。
- `mail.enabled = true` 时 `mail.host` 必填。
- 引导管理员 4 项要么整组配置、要么全部留空（见 3.6.1）。
- 枚举与布尔/整数格式合法性。

### 4.1 生产环境附加校验

`APP_ENV=production` 时额外强制：

1. 不得沿用开发占位会话密钥 `dev-only-change-me`。
2. `session_secret` 长度不得少于 32 字符。
3. `cors_allowed_origins` 不得包含 `*`。

第 3 条直接修复 Python 版本的安全缺陷：生产环境使用 `allow_origins=["*"]` 且允许凭据，
在浏览器规范下既是配置错误，也让任意站点可携带用户 Cookie 发起请求。

## 5. 敏感值边界

- `config.toml`、`.env.example`、`docker/config.test.toml` **只包含字段名与占位符**，
  不得写入真实密码、令牌或私钥；`.gitignore` 忽略 `.env`、`.env.local`、`*.local.toml`。
  （`docker/config.test.toml` 与 `docker/test.env` 中的值是**测试依赖凭据**，
  与 PostgreSQL/Redis 的测试密码同类，不代表任何真实环境。）
- 启动摘要（`Config.Summary()`）对 `database.password`、`redis.password`、`mail.password`、
  `session_secret`、`bootstrap_admin_password` 只输出 `set` 或 `unset`，绝不输出内容。
  `bootstrap_admin_username` 不是敏感值，会原样输出，便于运维确认初始化对象。
- 数据库连接串在日志与错误信息中一律使用 `RedactedDSN()`。
- 错误响应绝不包含堆栈、SQL 语句或物理路径；未识别错误统一为 500 `internal_error`，
  内部原因只进日志。

## 6. `updated_at` 语义（迁移相关的重要约定）

数据库 schema **不引入** `ON UPDATE` 触发器。`updated_at` 由应用在每条写语句中显式推进：

```sql
UPDATE projects SET name = $1, updated_at = now() WHERE id = $2 RETURNING updated_at;
```

理由：

1. 显式写出比隐式触发器更易审查，且与 `RETURNING` 一起保证"回读到的就是数据库真实值"。
2. 客户端的 `expected_updated_at` 版本协议完全依赖 `updated_at` 真实推进；
   触发器与 ORM 两种机制混用会让"版本何时变化"变得难以推理。
3. Python 版本把更新放在 ORM 层（`onupdate=now()`），数据库没有触发器，
   且更新后读取该属性会触发隐式同步 IO 并抛异常。

该语义由集成测试 `TestUpdatedAtMustBeAdvancedExplicitly` 锁住：单纯 `UPDATE` 其他列
不会改变 `updated_at`，显式 `SET updated_at = now()` 必须推进。

## 7. 运行

### 7.1 启动 HTTP 服务

```powershell
go run ./cmd/api
# 或
make run
```

启动日志依次输出：配置摘要（脱敏）→ 数据库连接池就绪 → Redis 客户端就绪 → HTTP 服务已启动。

收到 `SIGINT`/`SIGTERM` 后进入优雅关闭：停止接收新请求，等待在途请求完成，
超过 `server.shutdown_timeout_seconds` 后强制结束。

### 7.2 使用测试依赖运行

```powershell
make deps-up            # 启动 PostgreSQL 15432 / Redis 16379 / Mailpit 11025
make migrate-test-up    # 对测试库应用迁移
make run-test-config    # 以测试依赖启动服务（并初始化引导管理员）
make smoke              # 端到端冒烟检查
```

`make run-test-config` 除数据库/Redis 之外还注入测试用的引导管理员凭据
（`TEST_BOOTSTRAP_ADMIN_*`，与 `docker/config.test.toml` 一致），
因此冒烟脚本可以覆盖管理员端点的成功路径。

> **顺序有要求**：引导管理员只在**服务启动时**初始化一次。若在服务运行期间执行过
> 集成测试（测试会 TRUNCATE 业务表，把引导管理员一并删掉），
> 需要**重启服务**再跑冒烟。冒烟脚本在管理员登录失败时会给出这条提示。

### 7.3 初始化引导管理员

首次部署时按以下顺序操作一次即可（详见 3.6.1）：

```powershell
# 1) 迁移 + 准备依赖
make migrate-up

# 2) 注入一次性初始化凭据并启动
$env:SECURITY_BOOTSTRAP_ADMIN_USERNAME = "admin"
$env:SECURITY_BOOTSTRAP_ADMIN_EMAIL    = "admin@example.com"
$env:SECURITY_BOOTSTRAP_ADMIN_PASSWORD = "<随机字符串>"
go run ./cmd/api
# 启动日志会出现：
#   msg="引导管理员已创建" user_id=... username=admin
#   msg="引导管理员密码为一次性初始化凭据，账号创建完成后建议从配置中移除"

# 3) 用该账号登录，创建其余用户（本系统面向内部小组，通常只需要这一个管理员）
```

**初始化完成后**有两种可行状态，二者选其一：

- **整组移除**（推荐）：账号已经在库里，不再需要每次启动去确保角色。
  这是"录入一次"的本意。
- **整组保留**：每次启动都会确保该账号仍是系统管理员（例如它被误降级后能自愈）。
  这份一次性密码不会造成风险，因为账号已存在时它**不会被使用**。

**不可只移除密码**：校验要求整组配置或整组留空（见 3.6.1），
只留用户名会导致启动失败——这是刻意的，避免出现"看起来配了、实际什么都没做"的空配置。

## 8. 数据库迁移

迁移使用 `golang-migrate` 风格成对 SQL 文件，位于 `internal/database/migrations/`，
通过 `go:embed` 编译进二进制，因此部署物自包含、无需额外挂载迁移目录。

### 8.1 命令

```powershell
go run ./cmd/migrate up                # 应用全部未执行的迁移
go run ./cmd/migrate down              # 回退全部迁移（清空 schema）
go run ./cmd/migrate steps -1          # 相对当前版本后退 1 步
go run ./cmd/migrate version           # 输出当前版本与脏标记
go run ./cmd/migrate force 0           # 人工修复：强制设置版本并清除脏标记
```

`version` 在检测到**脏状态**时返回非零退出码。脏状态意味着上一次迁移中途失败，
必须人工介入，绝不能让 CI 在 schema 不确定的情况下继续跑测试。

### 8.2 目标库选择

```powershell
$env:DATABASE_URL = "postgres://user:pass@host:5432/dbname?sslmode=disable"
go run ./cmd/migrate up
```

迁移命令与 API 服务使用**完全相同的配置加载路径**，因此不会出现"迁移到了 A 库、
服务连的是 B 库"。迁移日志会打印脱敏后的目标库，便于确认。

迁移使用独立的 `database/sql` 连接（`golang-migrate` 需要会话级咨询锁），
不复用 API 服务的 `pgxpool`。

### 8.3 迁移规范

1. `up` 与 `down` 必须成对且可逆，`down` 后可再次成功 `up`。
2. 内容必须可重复执行、可审查；禁止在生产库手工修改表结构作为常规流程。
3. 外键删除行为必须显式声明（RESTRICT / CASCADE / SET NULL），不得依赖默认值。
4. 所有枚举字段必须带 `CHECK` 约束。
5. `project_members`、`task_members` 必须保留 `WHERE role = 'owner'` 的部分唯一索引。
6. 时间列统一 `TIMESTAMPTZ`；业务日期列使用 `DATE`。

新增迁移时，同步更新《02-数据库模型与迁移.md》与《05-迁移映射与差异.md》。

## 9. 测试配置

### 9.1 测试文件位置约定（已决策，2026-10-11）

**测试文件与被测代码同包、同目录**（Go 官方推荐做法），不集中到顶层 `tests/`。

曾评估过"把测试集中到与 `internal` 同级的 `tests/` 目录"这一习惯性方案，结论是**不采用**。
理由均为 Go 语言的硬约束，不是风格偏好：

1. **位于其他目录的测试无法访问包内未导出标识符**。实测确认：`tests/lib` 中引用 `lib.secret`
   会编译失败（`name secret not exported by package lib`）。
2. 为搬迁而导出内部实现会**削弱封装**。本仓库有多处测试直接验证私有实现细节
   （`config.readEnvFile` 的 `.env` 解析、`config.describeSecret` 的脱敏语义、
   `httpapi.errorStatus` / `errorMessage` 映射表完整性、`platform.decodeArgon2Hash`
   对非法摘要的处理）。其中 `decodeArgon2Hash` 的错误用 `%w` 包装，导出还需额外重构
   5 处 `fmt.Errorf`。
3. 导出这些符号**只为测试服务**，不构成有意公开的 API，会让"哪些是稳定对外契约"变得模糊。
4. **测试辅助与替身的位置难以兼顾**：集成测试装配、Auth 的 `Fake*` 替身若要被跨目录测试复用，
   必须移入普通（非 `_test.go`）包，从而进入生产二进制的依赖图。

保留同包测试，并以下列约定保持结构清晰：

| 测试类型 | 位置 | 命名 |
| --- | --- | --- |
| 单元测试 | 与被测包同目录 | `<subject>_test.go` |
| 测试专用辅助 | 同包内、文件名以 `_test.go` 结尾 | `helpers_test.go`（不进入生产构建） |
| 集成测试装配 | `internal/testsupport/`（专用包，只被测试导入） | `harness.go` + 各域 `*_test.go` |
| HTTP 层测试 | `internal/httpapi/router_test.go` | — |
| 端到端冒烟 | `scripts/smoke.ps1` | — |

若未来引入前端或**不属于任何 Go 包**的独立可执行验收测试，可在顶层新建 `tests/`；
但**不得**把包内单元测试迁出。

### 9.2 依赖地址覆盖

集成测试的依赖地址可通过环境变量覆盖（默认值对应 `docker/compose.test.yml`）：

| 变量 | 默认值 |
| --- | --- |
| `TEST_DATABASE_DSN` | `postgres://project_builder_test:...@127.0.0.1:15432/project_builder_test?sslmode=disable` |
| `TEST_REDIS_ADDR` | `127.0.0.1:16379` |
| `TEST_REDIS_PASSWORD` | `project_builder_test_redis_password` |

集成测试使用 Redis 的 **DB 15**，与开发用 DB 0 隔离。

### 9.3 串行化约定

集成测试共享同一个物理数据库，`TRUNCATE` 会清掉并发用例的数据。因此：

- 集成测试**不得**使用 `t.Parallel()`。
- 测试包通过 `TestMain` 获取 PostgreSQL 咨询锁（`pg_advisory_lock`），
  把 `go test ./...` 下并行执行的多个测试包串行化。
- `make test` 额外使用 `-p 1` 显式串行编译。

这套机制解决的是实测过的假故障：并发用例互相清空数据，表现为"注册返回 409"
或"查不到刚写入的用户"，与真实缺陷难以区分。

### 9.4 脏状态自愈

若上一次迁移被中断（例如测试进程被强杀），集成测试入口会检测到脏状态并重建
`public` schema 后重新迁移。否则一次中断会让之后所有集成测试永久失败。
