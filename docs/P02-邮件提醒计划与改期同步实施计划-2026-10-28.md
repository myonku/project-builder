# P02 邮件提醒计划与改期同步实施计划

> 建立日期：2026-10-28。状态：实施中（2026-10-29）；全仓文档同步与计划归档不属于本轮。
>
> 本文记录本轮已确认的目标规则与实施验收边界，不代表运行中的系统已经具备这些能力。当前交付规范仍见 [S01](S01-需求文档.md)、[A08](api/A08-reminders.md) 和 B/F 文档；实施前按阶段同步契约，完成后统一收口设计并归档本计划。
>
> 2026-10-29 设计复核：仅补齐发送互斥、结果分类、同日抑制和事件身份边界；采用现有 PostgreSQL 与 pgx，不新增缓存、MQ 或任务框架。随后用户已授权实施；实现分支为 `codex/p02-reminder-scheduling`。本轮只更新本文，不修改其余规范文档，最终同步及归档另行安排。

## 1. 目标与现状

将“后台扫描任务，在提醒日生成记录”改为“业务变更时同步持久化提醒计划，后台领取到时计划并发送”。专门的提醒计划模块统一承担日期计算、收件人确定、计划更新/失效和去重，不再由各业务模块分别计算发送时间。

当前实现的缺口：

- `reminders.Generate` 周期扫描任务，只在提前提醒日生成开始前/到期前提醒，错过该日后不能正确补发。
- 普通任务更新与 `/tasks/{id}/dates` 均未同步既有计划；旧 pending 记录仍按旧时间派发。
- 派发重新读取当前任务日期，但没有校验原计划是否仍适用，可能在错误时间发送带新日期的旧提醒。
- 延期提醒使用固定 `once` 去重，任务改期后再次逾期不能开启新的提醒周期。
- 现有任务事件提醒在提交后尽力记录，失败仅记日志；该方式不足以保证计划与业务事实一致。

交付基线：HTTP 69 个端点，数据库迁移 head 10。本计划预计新增数据库迁移；编号以实施时实际 head 为准，不预占号码。

## 2. 范围与不包含事项

### 2.1 本轮范围

- 任务开始前、到期前、逾期，以及既有分配/持有者变更提醒纳入统一计划管理。
- 项目/任务更新及其关联成员、收件人资格变化触发计划同步。
- 支持反复改期、取消/恢复、归档/解除归档、删除及汇总派生状态变化。
- 到时派发、同日去重、失败处置、并发有效性检查、旧数据迁移和验收证据。
- 提醒列表/详情/重试入口适配新的计划生命周期；仍按现有权限隔离数据。

### 2.2 不包含事项

- 甘特图拖拽编辑：作为后续独立功能，使用本轮交付的日期同步能力。
- 新增项目节点提醒类型、周期重复任务、整棵任务树批量平移。
- 密码重置邮件改为异步；其令牌、冷却、发送链路保持独立。
- 法定节假日/调休日历、跨渠道通知、邮件内容营销或批量群发平台。
- 对历史邮件补发、撤回或保证收件箱必达；SMTP 接受与用户实际收件仍区分记录。

## 3. 已确认业务规则

### 3.1 日期、时间与适用状态

1. 任务日期为 `YYYY-MM-DD` 自然日；计划转换成 UTC 时刻持久化。提醒日与 9 点按收件人的 IANA 时区计算。
2. “提前一天”继续表示提前一个工作日，工作日为周一至周五，不含法定节假日调整。例如周一节点在上周五提醒。
3. 截止当天未逾期，截止次日开始逾期。今天为 10 月 28 日时，截止 10 月 28 日不能立即发逾期提醒；截止改为 10 月 27 日才属于直接逾期。
4. 项目归档、项目/任务删除、任务完成或取消、收件人不合格时，不保留可发送计划；已发送历史保留。
5. 开始前提醒适用于尚未开始且开始日期尚未到来的任务；任务已开始后不补发“即将开始”。到期前及逾期提醒适用于所有未完成、未取消的有效任务，包括尚未开始的任务。本项明确替代当前“未开始任务不生成到期前提醒”的限制，阶段一须同步需求及契约说明。
6. 父任务使用 P00 持久化的有效状态，不单独推导另一套完成/取消结果；日期仍是该任务自己的日期，不自动取子任务日期包络。

### 3.2 计划时间和补发

| 情况 | 处理规则 |
| --- | --- |
| 正常开始前/到期前提醒 | 节点前一个工作日，当地 09:00 |
| 自然进入逾期 | 截止次日当地 09:00；提前建立计划，不依赖当天扫描任务 |
| 同步时提醒日为今天，尚未到 09:00 | 保留今天 09:00 的计划 |
| 同步时提醒时间已过，开始日期仍在未来 | 尽快补发开始前提醒 |
| 同步时提醒时间已过，截止日期尚未过去 | 尽快补发到期前提醒，截止当天仍可补发 |
| 同步时开始日期已到或已过 | 不补发开始前提醒 |
| 改期、新建、恢复有效状态时已经逾期 | 取消过时的到期前计划，逾期提醒立即入队，不等下一个 09:00 |
| 服务停机后恢复，计划已到时 | 先按当前事实检查有效性，再尽快派发；已经逾期的任务不再发“即将到期” |

“立即/尽快”均指入队后由后台处理，受派发周期、批量和节流约束；业务 HTTP 请求内不执行 SMTP。普通名称/描述更新不得将原定 09:00 的逾期计划提前，也不得重置已发送标记。后台恢复时对已过期的提前提醒应由计划模块转换为适用的逾期计划，而非静默丢失；该转换只处理已有到时计划所关联的任务，不恢复全量任务扫描。

### 3.3 已发送、未发送与提醒周期

- 改期前已发送的邮件保留原始发送记录和内容快照；新日期允许生成新一轮提醒，但仍受同日去重约束。
- 改期前未发送的计划同步到新规则算出的时刻；同一种有效提醒不保留两个待发副本。同步不得把旧失败计划继续留在旧日期供人工重试。
- 只有相关节点日期实际变化才开启该节点的新日期周期；开始日期变化不重置截止节点周期，反之亦然。普通编辑、重复提交相同日期、后台重复同步不创建新周期。
- 日期 A → B → A 属于新的日期安排，允许再次提醒；若落在当天且同类已发送，仍不再生成重复待发计划。
- 持续逾期且截止日期未变化时，每位收件人在该截止周期只发一次，不变成每日催办。跨日重复编辑、归档后解除、取消后恢复，均不能仅凭重新同步绕过这一限制。
- 取消/归档等失效操作不擦除日期周期和发送事实。恢复时按当前周期及当前有效性重新计算；未来计划可以恢复，已发送的同周期提醒不重复发送。
- 分配及持有者变更属于业务事件，普通改期不得凭空产生新事件邮件。事件发生后若等待发送期间任务或收件关系失效，则取消；重新发生真实事件按事件规则处理，并受同日去重约束。

事件身份采用以下最小规则，不另建通用事件总线：

- 沿用现有分配/持有者变更触发入口；成员关系从不存在变为存在才是新分配，持有者实际转移给该用户才是新的持有者变更。重复保存、添加已存在成员、转移给当前持有者均不产生新事件。
- 移除后重新加入、持有者转出后转回均属于新事件，允许在不同实际发送日再次提醒；这明确替代旧分配提醒的终身 `once`。事件 ID 在业务事务中生成并随计划保存；现有请求幂等重放复用原结果，事务回滚不留下事件。
- 同一任务/收件人/类型的新事件出现时，旧的未获发送授权的事件计划被替代，当前只保留最新一个待发事件；旧事件身份及替代原因保留。已获授权的尝试不可改写，新事件等待该尝试结算，再接受实际发送日去重。
- 开启提醒、恢复账号或恢复任务有效性只重算节点提醒，不复活已取消的历史事件；只有新的真实关系变更才产生新事件邮件。不同提醒类型仍互不抵消。

### 3.4 同日去重

去重范围为 **任务 ID + 收件人 ID + 提醒类型 + 收件人当地自然日**。不同任务、不同人、不同类型互不抵消；同日已成功发送优先于“新日期可新发”的规则。

- 同步时：相同计划日的同类有效待发计划合并；当天已发送时不创建当天的重复待发计划。改至将来另一天的计划仍可创建。
- 派发时：按实际发送日再次判重。昨天积压的同类邮件和今天的计划不能在今天各发一封。
- 已取消、被替代、发送失败和明确未发送的记录不占成功发送名额；正在发送的记录需要独占领取，不能另起并发发送。
- 去重按用户身份，不按邮箱字符串。修改邮箱不重置发送记录；修改时区也不能清空去重历史。计划按新时区重算，实际历史使用 `sent_at` 在当前时区投影判重，并保留原发送时区/自然日用于追溯。
- 同一节点周期“已经成功发送一次”与“当天已经发送同类”同时约束；跨日积压补发后不得再以原计划日重发。
- 示例：今天已发送一次逾期提醒，截止延后又改回逾期日期，不创建第二条今天待发计划；若新的日期周期在另一天进入逾期，则允许新提醒。

同日去重命中时，应保存当前周期/事件的 `suppressed` 终态及其覆盖的成功尝试 ID，而非只跳过插入。节点提醒以“周期 ID + 收件人 + 类型”、事件提醒以“事件 ID”标识本次被抑制的对象；抑制不伪造成功事实、不增加 SMTP 尝试次数，也不改写被引用的旧发送内容。该周期/事件此后不会因跨日编辑、恢复、时区变化或手工重试再次排队。日期实际再次变化或发生新事件才能产生新的对象，且仍需判重。仅当计划已到时，或新计划算出的应发时刻已过、需要当日补发时，才按当天成功事实作终态抑制；未来另一天的计划不能被今天的成功提前抑制。

## 4. 同步触发边界

| 变化来源 | 必须同步的范围 |
| --- | --- |
| 创建、复制任务 | 新任务及按既有权限/成员规则确定的收件人；复制不复制发送历史 |
| 普通编辑、专用日期接口 | 目标任务；按实际日期差异决定周期；相关状态变化一并处理 |
| 完成、取消、删除及恢复 | 目标任务和受 P00 汇总影响的祖先；删除父任务时不能误取消仍存活子任务的计划 |
| 添加/删除子任务、同项目改父级 | 受影响的原/新祖先链，包含首末子任务切换导致的状态变化 |
| 项目归档、解除归档、删除/恢复 | 项目内相关任务；项目日期变化不擅自改写任务日期或新增项目邮件 |
| 任务成员/持有者变化 | 受影响收件人及真实事件提醒 |
| 项目成员、权限、工作组资格变化 | 按当前收件人规则重算受影响任务；有读取权限不等于自动订阅所有任务 |
| 用户邮箱、时区、提醒开关、停用/恢复 | 该用户相关计划；开启/恢复不补发历史分配事件，当前节点提醒按补发规则计算 |
| 名称、描述等内容变化 | 不改变周期/计划时间，发送时使用当前有效内容；已发送快照不改写 |

不新增任务恢复 HTTP 接口。存储层恢复路径和维护操作必须通过统一同步入口，或在恢复事务后执行显式修复流程，不能依赖下一次全量扫描自愈。涉及工作组/项目有效性的既有操作先形成影响清单，不遗漏间接收件关系变化，也不扩展当前权限。

## 5. 模块与一致性约束

### 5.1 职责

- **规则计算**：纯函数接收任务有效事实、节点周期及其发送/抑制结果、收件人、时区、成功/未知发送事实与当前时间，输出应有计划及失效原因；可用可控时钟验收。
- **计划同步**：在业务事务内读取更新后的最终状态，新增、调整或取消计划；以数据库唯一约束保证重复调用幂等。不能只在提交后调用并记录失败日志。
- **派发**：只查询到时计划，领取发送资格、校验有效性与去重、调用补齐结果分类后的 Sender、记录结果。停止旧 `Generate` 周期任务扫描。
- **历史与排查**：区分当前计划、节点周期和发送尝试/成功事实；保留变更原因、业务版本、计划时间、实际发送时间、收件地址与必要内容快照。

业务更新和计划同步同库提交，SMTP 不在业务事务内。大型项目或用户影响多条计划时采用批量 SQL 和确定锁顺序；若容量验证证明必须异步同步，应先修订方案，引入同事务持久化的同步事件及派发屏障，不能自行降级为提交后的尽力调用。

### 5.2 并发、派发及失败

- 延续项目先于任务的既有锁顺序，补齐计划领取与去重锁顺序；多个实例也只能领取一次同一有效发送资格。
- 领取与发送授权合为一次短事务：锁定项目、任务和该发送范围的门闩，重新读取有效性、收件关系、周期/事件及当天发送事实，写入唯一尝试令牌、内容/地址/时区快照，将计划转为 `sending` 后提交。候选列表只提供 ID，不提供可复用的发送许可；只有本进程明确确认该授权事务已提交，才能调用一次 Sender，提交结果未知时不得发信。
- 上述授权事务的提交是改期与发送的裁决点：业务变更先提交，旧计划不能获授权；发送授权先提交，该快照允许完成，之后的变更只调整尚未获授权的计划。这一边界可能早于实际建立 SMTP 连接，不能表述成“改期提交前尚未连 SMTP 就一定可撤销”。SMTP 期间不持有业务行锁或数据库长事务，不承诺数据库与外部 SMTP 原子提交。
- SMTP 明确失败与“连接中断、可能已接受”分开记录；后者记为结果待核实并阻止盲目自动重发，不伪装成成功或安全失败。发送成功后数据库落账失败也按不确定结果处理。
- 为减少状态和竞态，本轮不增加可自动回收的“已领取、尚未授权”阶段。已授权尝试超过截止时间未结算一律转 `unknown`，即使实际崩溃在调用 SMTP 前也不自动重发；代价是少量明确未发出的邮件也可能需要人工处置。截止时间用于发现异常，不表示可以换进程接管发送。原进程恢复时须核对令牌/状态并遵守发送超时，不得重新发送；已获授权的旧进程仍可能恢复执行，所以未知结果解除还需满足 §5.4 的停派发条件。
- 人工重试需重新经过有效性、同周期及实际发送日去重；不能绕过取消/归档或直接复用旧日期。保持现有“不进行无限自动重试”的边界，有限重试策略如需加入须在本计划登记。
- 派发具备可配置节流和单轮批量上限；同日去重不能代替 SMTP 频率控制。测试默认 FakeSender/Mailpit，不使用聊天中的真实凭据；真实外发须单独明确授权并限制封数。
- 邮件发送开关关闭时暂停派发，不丢失未来有效计划；重新启用后按当前状态过滤并节流处理到时积压，避免启动即集中外发。收件人主动关闭提醒则使其计划失效，二者含义分开。

### 5.3 数据与接口落地要求

阶段一确定字段、表及状态映射，再实施迁移；不将以下概念继续挤入旧 `dedupe_key`：

1. 节点周期及其目标日期；每任务、每收件人、每类型当前有效计划的唯一性。
2. 成功发送事实及发送尝试，支持按实际发送日去重及不确定结果隔离。
3. 取消/替代原因、领取状态和版本，区别于普通失败；同步更新不覆盖历史证据。

可复用或拆分现有 `reminders` 表，但必须表达上述约束。提醒 API 的 pending/sent/failed/skipped 与新增生命周期状态、重试资格、列表排序/分页、详情展示须有明确映射；任何新增响应字段/状态先更新 A08 和前端类型，不默默改变含义。原则上复用现有端点，不新增对普通用户开放的计划维护接口。

### 5.4 本轮采用的最小持久化与处置方案

**依赖与数据职责**：继续使用 PostgreSQL 事务、唯一约束、行锁和现有 pgx；Redis 不参与提醒发送资格、周期或成功事实的正确性判定。不引入 MQ、分布式缓存锁或工作流框架。消息队列不能消除 SMTP 接受与数据库落账之间的不确定性，反而还需维护业务库与队列的一致性；只有容量验证确有需要时才另行评估。依据：[PostgreSQL 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)、[RabbitMQ 可靠性与重复投递边界](https://www.rabbitmq.com/docs/reliability)。

在现有计划模型基础上，默认只新增以下两类表；具体 DDL 和对外状态映射仍在阶段一确定，不另拆周期表、事件总线表或每日锁表：

| 存储 | 最小职责与约束 |
| --- | --- |
| 扩展现有 `reminders` | 保存周期/事件身份、计划版本、当前状态、失效/抑制原因及覆盖尝试引用；未授权的有效待发计划按任务/收件人/类型唯一。任务行分别保存开始/截止日期的单调周期号，实际日期变化时同事务推进，取消/恢复及没有合格收件人时也不丢失周期。历史计划不覆盖；已授权的旧尝试与改期后的新计划可并存，但新计划不能越过门闩发送。 |
| `reminder_delivery_guards` | 按 `(task_id, recipient_id, kind)` 主键保留一行，保存当前活动尝试引用。行本身作为跨周期、跨事件、跨日的互斥点；`sending` 或未解决的 `unknown` 均阻挡该范围内的新发送。业务改期仍可提交和更新未来计划，不因门闩占用而被禁止。不能按周期或日期拆门闩，否则改期会绕过隔离。 |
| `reminder_delivery_attempts` | 每次获授权的 SMTP 尝试一行，保存唯一令牌、计划/周期/事件版本、授权时间、截止时间、不可改写的内容/地址/时区快照，以及发送结果和证据。成功记录即去重事实来源；同范围判重在持有 guard 行锁时查询该历史，不再维护另一份每日成功计数。 |

**事务协议**：同步、授权、结算、重试和维护命令都使用同一门闩。业务变更先按既有事务写入最终事实，再同步计划；授权按“项目 → 任务 → guard → 计划/尝试”的顺序取锁后重新读取事实，结算也采用相容顺序；多对象按稳定 ID 顺序。所有资格变更路径必须在同事务提交前经过相同的计划同步/门闩，不能仅在派发时读取用户开关而没有写侧互斥。阶段一须列明用户、组及多项目操作已有锁与上述顺序的关系，消除反向取锁，不能在授权事务末尾随意追加用户/组行锁。

**最小状态流**：计划 `pending → sending → sent / failed / unknown`；未授权计划还可转 `cancelled / superseded / suppressed`。`failed` 只用于有明确未接受证据的发送失败；全局发送关闭保持暂停，不转失败。历史 `skipped` 保留，并按原因映射重试资格。只有 `pending` 可以获得发送授权；`sending` 与 `unknown` 都不可通过现有 retry 接口重新发送。

- 结算以尝试令牌作条件更新，只能更新属于本次授权的尝试和关联计划；旧尝试返回不得覆盖新计划、清除别的活动令牌或擦除人工处置。授权后即便业务已改期/取消，也必须保存其真实发送结果。成功结算后，当前已到时的新计划应按成功事实记录抑制，未来计划继续保留。
- 明确未接受时，保存失败并释放活动引用；人工重试仍先检查当前资格、周期、去重及其他未知尝试。已被替代的失败计划不得直接复活。成功时保存事实并释放活动引用。结算落账失败则 guard 继续占用，由超时检查转未知；不得因保存结果失败再次调用 Sender。
- 未知结果不计作成功，也不释放门闩；改期、跨日、换邮箱/时区、移除再加入均不能绕过。尝试本身不会永久停留在 `sending`，但该范围有意暂停到人工核实；其他任务/用户/类型不受影响。
- 本轮使用管理员维护命令处置未知结果，不增加普通用户写接口。处置前暂停全部派发实例并确认原工作进程已终止，单纯租约过期或开关关闭不足以证明旧进程不能继续发信。管理员提供依据，记录操作者、原因和证据：确认已接受则补成功事实及可确认的接受时间；明确未接受则释放后按当前事实重算计划，历史事件不复活；仍无法确定则保持隔离。无法确定接受时间的记录不伪造 `sent_at`，继续隔离等待核实。命令同样受令牌条件更新保护且不执行 SMTP。

**Sender 的最小改造**：保留 `Send(ctx, Message) error` 接口形状，在现有 mail 包内增加可用 `errors.As/Is` 判断的结果错误类型。`nil` 表示 SMTP 最终接受已明确确认；明确拒收/确认未提交的错误允许归类为未接受；正文提交后未拿到最终回复、或无法证明未接受的普通错误，保守归为未知。最终接受已确认后，`QUIT` 失败或之后的上下文取消只能作为诊断信息，不能改写为失败/未知。正文写入失败的清理不得再尝试提交正文；FakeSender 与 SMTP 实现采用同一分类约定，不靠错误文案判断，也不新增邮件库。该改造保留密码重置的同步调用方式，不顺带引入其异步队列。

## 6. 迁移、切换与回退

1. 先备份并停业务写入及旧派发器，确认没有旧实例继续生成/发送。
2. 应用迁移：保留旧 sent/failed/skipped 与尝试证据，建立新周期、计划及去重事实。旧 pending 逐条按当前有效任务/用户状态重算，不照搬旧时间。
3. 旧 sent 以真实 `sent_at`、任务、收件人和类型导入发送事实；历史发送时区无法还原时使用当前用户时区投影并标注来源，不能声称恢复了原始时区。旧事件无可靠周期时按当前节点建立保守历史映射，避免升级引发整批补发；迁移报告列出该兼容决策和数量。
4. 一次性遍历存量有效任务初始化未来计划，允许有进度、校验和可重复执行的维护命令；这不作为常驻任务扫描保留。
5. 先在禁止 SMTP 外发模式下检查计划数量、取消数量、同日重复、近期待发及补发分布；历史已过期周期不全量补发。首次上线的逾期积压需列明并采取显式发布放行/节流，不默认一次全部发出。
6. 部署新后端及必要前端，确认旧生成链路停止，再受控开启派发；验证健康、积压、重复领取和失败观测。
7. 回退前停新派发并备份所有新发送事实，禁止恢复旧快照后忘记新邮件已经发出。没有完成旧版本可识别的历史映射前，不重启旧扫描生成器；无法安全降级时保持邮件派发暂停，业务回退方案单独执行。

旧 `failed` 不能仅凭状态名导入为“明确未接受”：旧 Sender 曾把接受后的退出会话错误也归为失败。保留原状态/错误作为历史证据，缺乏明确未接受证据的旧失败在允许重试前按未知结果隔离并建立相应门闩，由管理员依 §5.4 处置；不得通过迁移或初始化自动重发。迁移报告分别列明此类数量与已确认安全失败数量。

初始化命令、只检查模式、切换与回退演练使用独立数据库及 Mailpit，不能操作日常开发/生产数据。

- 统一数据库规则函数 `reminder_schedule` 显式接收时钟；数据库中损坏的旧时区值回退 UTC，与既有读取行为一致。`reminder_task_cycles` 只在日期实际变化时推进相应周期；延迟同步读取事务最终状态，覆盖 P00 祖先变化、成员与资格、归档/恢复、逻辑删除/恢复。名称/描述/进度等不影响资格或节点的变动不重排计划。P00 内部无实际相关变化的行更新跳过重复同步。
- 新派发器只查询已到时的 pending ID，授权时重新读取事实与日去重；旧任务扫描器和提交后事件记录适配器已移除。短事务提交发送快照和唯一 token 后才调用 Sender；结算失败不再次调用 Sender，过期授权转 unknown、保留 guard。旧 token 不得覆盖新计划或人工结论。
- 运维互斥使用数据库共享/排他咨询锁：派发轮次持共享锁，初始化/未知处置持排他锁，SMTP 期间无业务行锁或长事务。运维锁使用独立连接，避免 `max_conns=1` 时占尽业务连接池；该场景已有真实数据库回归。
- 阶段回归覆盖多实例、改期先后、同日抑制跨日、授权超时、晚到回执、发送后落账故障、同步故障回滚、收件开关/邮箱/时区、事件移除后再加入、初始化和迁移。故障注入产生的预期 500 只属于测试，不作为通过依据；断言验证事务确实回滚。

**本轮 API 差异（后续再同步 A08/F02）**：端点及作用域不变。新增 `sending / unknown / cancelled / superseded / suppressed` 状态，历史 skipped 保留；原字段仍保留。新增 `cycle / plan_version / covered_by / event_id / can_retry`，详情还返回本人可见提醒的 `delivery_attempts`（授权时间、截止时间、结果、时区、收件地址/主题/正文快照、错误）。列表该历史字段为 null，避免分页响应携带全文；重试按钮以服务端 `can_retry` 为准，服务端仍在事务内复核。未授权取消/抑制不计尝试，实际获得发送授权才计一次；全局邮件关闭保留 pending、attempts 不增加，重复 retry 返回 409。未知结果只由运维命令核实，普通 API 不能重发。列表排序/分页沿用现有白名单和 ID 次级排序。

**调度配置**：`scheduler.reminder_send_interval_ms`（环境变量 `SCHEDULER_REMINDER_SEND_INTERVAL_MS`，默认 1000、可设 0）与 `scheduler.reminder_attempt_timeout_seconds`（`SCHEDULER_REMINDER_ATTEMPT_TIMEOUT_SECONDS`，默认 120、须为正数）；原批量上限仍生效。节流是每个派发实例的间隔，不宣称服务商额度或多实例总发送速率；上线按实例数配置。未知结果不自动重发，有限自动重试未加入。

### 10.2 本轮运维入口

在 `backend/`、使用与 API 一致的配置及明确的目标测试/生产库运行 `go run ./cmd/reminders <操作>`。该命令不构造 Sender，不执行 SMTP：

- `inspect`：按生命周期统计总量与到时量。
- `initialize`：默认只检查并回滚；`initialize --dry-run=false --dispatchers-stopped` 应用，默认不放行既有逾期积压。确认积压后增加 `--allow-overdue` 才放行。逐项目提交是可重复执行的检查点；派发必须停用直到全部初始化、检查及放行完成。
- `resolve --attempt <ID> --actor <管理员ID> --outcome accepted --sent-at <实际接受时间RFC3339> --evidence <依据> --dispatchers-stopped`：补已接受事实。明确未接受使用 `--outcome not_accepted`，不提供 sent-at；无证据保持隔离。操作者、证据、结果及时间保存在尝试 resolution 中，命令拒绝非启用管理员、已处理 token、缺少停派发确认，以及仍有派发轮次持锁的情况。旧事件不复活，节点计划按当前事实重算，明确失败继续经过人工重试。
- `export`：以 JSONL 导出尝试及发送事实，供回退前备份；含收件信息/内容，输出应重定向到受保护文件。导出完成和校验前不得应用 down。降级后旧派发器继续保持暂停；该工具不把不兼容的新周期事实假装转换成旧版去重键。

测试只使用隔离的 `worklane-p02` Compose 卷、`worklane_p02_test` 数据库和同名 Mongo 数据库；不连接真实 SMTP。全量集成测试与针对同库的局部测试串行执行，避免互相清理 Redis 会话及测试数据。
