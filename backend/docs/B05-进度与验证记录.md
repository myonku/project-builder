> **配置不匹配时会得到 201 / 1 而不是 207 / 0**（2026-10-12 实测：182 断言时是 176/1，加审计与链路断言后同一差值）：脚本对"调度器已生成提醒"
> 的断言只轮询 30 秒，而 `config.toml` 的 `scheduler.interval_seconds` 是 60，因此必须把 interval 调成 5 秒。
> `docker/config.test.toml` 另有一套差异（`scheduler.enabled = false`、`mail` 指向 Mailpit），**不适用于冒烟**，其文件头已注明。
> **2026-10-21 追加**：`config.toml` 的 `security.registration_requires_approval` 默认为 `true`，
> 而冒烟会在注册后直接登录，因此必须显式传 `SECURITY_REGISTRATION_REQUIRES_APPROVAL=false`；
> 否则注册用户停在 `pending`、登录得到 401（实测 141 项失败）。

> **引导管理员是冒烟覆盖管理员成功路径的前提**：服务按测试配方启动时
> 会按 `security.bootstrap_admin_*` 初始化一个系统级后台账号（见《B03-配置与运行.md》3.6.1）。
> 该初始化只在**启动时**执行一次，因此若在服务运行期间跑过集成测试
> （测试会 TRUNCATE 业务表，把引导管理员一并删掉），需要重启服务再跑冒烟。
> 冒烟脚本在管理员登录失败时会直接给出这条提示。

```text

  [PASS] 缺少 arg 头被拒绝：422
  [PASS] GET /api/v1/health/check (带 arg 头) = 200
  [PASS] GET /api/v1/health/ready = 200

  [PASS] 响应未泄漏密码或摘要
```

> 于是缺陷被记为"没被拦住"。**验证脚本本身也会说谎**，它同样需要被核对

### 5.11 持有者转移修复（2026-10-11）

**问题**：`role: owner` 被映射为 `promote`，而 `promote` 在"已存在持有者"时被拒绝；
`demote` 又在"是唯一持有者"时被拒绝。两者叠加的结果是**持有者永远无法变更**，
而错误文案却写着"请先转移持有者"——系统里不存在这样的路径。

**根因**：把"持有者唯一"这一不变式当成了"不能有第二个"，却忘了它同时意味着
"设为持有者 == 从现任手里接管"。前者用部分唯一索引表达，后者必须由显式事务完成。

**修复**：新增领域动作 `transfer`；`role: owner` 现在表示**转移**，
在**同一事务**内先降现任持有者、再升目标（顺序不可反：反过来会立刻撞上"第二个 owner"，
而先降的中间态是"没有 owner"，绝不能提交）。拒绝路径保持清晰：

| 请求 | 结果 |
| --- | --- |
| 降级唯一持有者（`role: member`） | `403 permission_denied`（要换人请转移，不要两步） |
| 转移给普通成员 | `200`，原持有者降为 `member` |
| 转移给已是持有者的人 | `409 conflict` |
| 转移给非成员 | `404`，且**整体回滚**（持有者不会空缺） |
| 转移给已停用用户 | `422 validation_error`（否则项目立刻无人可管理） |

**验证**：`TestProjectMemberInvariants`（9 个子用例）、`TestTaskMemberMustBeProjectMember`、
`TestOwnershipTransferConcurrencyKeepsExactlyOneOwner`（用外部行锁强制两个转移请求
在写入前排队，断言结束后**恰好一个**持有者），以及 4 处变异验证（5.7 第 25–28 条）。
冒烟脚本新增 9 项断言覆盖上述全部路径。

**相邻的两项已在紧随其后的一轮修复**（工作组所有权转移、系统管理员放行），见 5.12。

### 5.12 所有权转移与管理员放行（2026-10-11）

**问题 1**：工作组所有权无法转移（`groups.owner_id` 一旦确定就永久固定）。
需求文档没有明确要求，但人员离职后该组会无人可管理。

**问题 2**：系统管理员不能转移项目/任务持有者，也不能读写自己不是成员的对象。
需求文档 4.1 把"管理所有用户、工作组和系统级数据，处理异常数据"列为管理员职责，
而实现里这条只在少数几处生效（用户管理、修改工作组），其余一律 404。

**根因（两个问题共同的、也是最值得记住的一点）**：
权限函数接收的是 `domain.User`，而用例层手上往往只有 `actorID`。
各处随手写 `domain.User{ID: actorID}`，`SystemRole` 因此恒为空——
"管理员放行"的代码写了、审了、也留了注释，却**从未生效过一次**，
而且没有任何报错：表现为管理员被当成普通成员。

这类缺陷（**字段被静默留空**）与前几轮踩到的"归一化丢字段""统计与列表不同源"
属于同一家族：不报错、不返回 5xx，只是行为与预期不一致。

**修复**：

1. **记录携带调用者的系统角色**。`GroupRecord` / `ProjectRecord` 增加
   `ActorSystemRole`，由查询一并取出（`JOIN users actor ON actor.id = $n`），
   用例层用 `actorOf(record, actorID)` 重建领域用户。
   刻意不在权限入口再查一次用户：那会引入第二次往返与第二份事实。
2. **领域层的权限函数对管理员放行**：`ProjectPermission`（→ `PermManage`）、
   `CanManageProject`、`CanManageGroupMembers`、`CanViewGroup`，并新增 `CanTransferGroupOwnership`。
   放行必须放在**其它条件之前**——否则一个被停用的工作组连管理员都改不了，
   也就没人能把它重新启用。
3. **SQL 可见性同步放行**：列表查询（`visibleCondition` / `visibilityCondition` /
   `groupScopeCondition`）必须让管理员查到全部对象，否则会出现
   "能改却看不到"的半截状态，管理员根本找不到要处理的对象。
   只改领域层或只改 SQL 都只能得到一半效果——这一点已写入 backend/docs/B01 §5.9。
4. **工作组所有权转移**：`PATCH /groups/{group_id}` 新增 `owner_id`，同事务内改写
   `groups.owner_id`，并把目标成员的 manager 行置为活跃、原所有者降为 `member`。
   放行边界同时明确：管理员豁免的是**权限判定**，
   不豁免归档只读、唯一持有者不可降级、任务成员必须是项目成员等状态规则与不变式
   （`TestAdminBypassDoesNotBreakInvariants` 逐条锁住）。

**验证**：`TestAdminCanReachDataWithoutMembership`（管理员对三域数据的读与管，
含列表不再按成员关系过滤，以及计划视图的只读聚合端点）、`TestAdminBypassDoesNotBreakInvariants`（放行边界 4 项）、
`TestAdminCanTransferOwnership`（三域所有权转移）、`TestGroupOwnershipTransfer`
（语义与 6 条拒绝路径）、领域单测 3 组，以及 7 处变异验证（5.7 第 29–35 条）。冒烟新增 6 项断言。
其中第 34 条是同一根因的**第三处**出现（projects、groups、planviews 各一处），
说明"随手构造 domain.User"是一个会反复发生的动作，而不是一次疏忽。

**写入规则的文档**：[backend/docs/B01 §5.9](./B01-Go服务端架构设计.md)（管理员放行及其边界、
两种必须避免的实现方式）与 §5.10（所有权必须可转移、同事务先降后升）。
这两条是"避免后续出现同样的问题"的落点：它们描述的不是某个模块的实现，
而是**每一处权限校验都必须满足的性质**。

### 5.13 Attachments（2026-10-11）

**实现范围**（人工确认的口径）：

- 端点 7 个：项目/任务各一组"上传 + 列表"，加下载、逻辑删除、彻底删除。
- 配额：单账号最多 1000 份（配置项），单项目/任务不限制。
- 扩展名单：全局可配置，空数组或 `["*"]` 表示不限制。
- 逻辑删除后的附件只对**上传者、容器持有者、系统管理员**可见，
  并支持**彻底删除**回收磁盘。
- **不做**回收站界面、过期自动清理、断点续传、多文件上传（人工确认收益有限）。

**三个需要解释理由的选择**（否则后来者很容易"顺手改回去"）：

1. **附件没有独立权限**，完全继承项目/任务。另立一套会立刻与项目/任务权限分叉，
   而"删除即对所有人隐藏"会让上传者自己都收拾不了传错的文件。
2. **彻底删除先删对象、再删行**。两种失败模式里，"对象没了行还在"可修复
   （`DELETE` 不存在的对象是幂等的，重试即成功），"行没了对象还在"不可见、
   永远占着磁盘且无人知道。因此宁可留下前者。
3. **配额计入已逻辑删除的附件**。它们仍占磁盘，彻底删除才是回收点；
   不计入的话，用户可以用"上传 + 逻辑删除"无限占用存储。

**存储层的边界**：`internal/platform/storage` 只有四个方法（Put/Open/Delete/Exists），
不含任何业务语义。本地实现写入用"临时文件 + 重命名"（同一文件系统内原子，
不会出现半截文件），并对 key 做严格校验：拒绝绝对路径、盘符、反斜杠、
空字符、`.`/`..` 片段，解析后再确认结果仍位于根目录之下。
`stored_key` 由服务端按 UUIDv7 生成，**绝不使用用户提供的文件名**——
原名只作为展示字段（`TestLocalRejectsEscapingKeys` 锁住这条边界）。

**过程中发现并修正的一处真实缺陷**：容器权限判定的返回约定是
`PermNone + nil error`（而不是错误），attachments 最初把 `PermNone` 直接当作
"无写权限"返回 `403`，于是**非成员能通过状态码区分"项目不存在"与"项目存在但无权"**。
这条在集成测试里立刻暴露（期望 404 实得 403），修正后统一为先判 `PermNone` → 404，
再判权限不足 → 403，与契约 7 的处理顺序一致。

**验证**：`TestAttachmentUploadAndDownload`、`TestAttachmentUploadRejections`（6 条拒绝路径）、
`TestAttachmentExtensionWhitelist`、`TestAttachmentQuota`（含"逻辑删除不释放配额、
彻底删除释放"）、`TestAttachmentSoftDeleteVisibility`（7 个子用例，

### 5.14 Reminders（2026-10-11）

**实现范围**（需求文档 5.7）：五种提醒类型（新任务分配/开始前/到期前/延期/持有者变更）、
固定周期派发、三个端点、失败原因与重试次数可查询、可重试。
`skipped` 与 `failed` 严格分开（邮件未启用、收件人不合格、任务不再适用 → `skipped`）。

**三个需要解释理由的选择**：

1. **由后台周期循环生成，而不是在写请求里发邮件**。需求既要求"按固定周期检查待发送提醒"，
   也要求"邮件发送不得阻塞用户操作"。事件型提醒（新分配、持有者变更）在写路径上
   **只插入一行**，发送仍交给循环。
2. **幂等靠 `dedupe_key` 唯一约束**，键含任务、收件人、类型与**时间窗口**。
   周期扫描必然重复运行，因此去重必须落在数据库上；键不含窗口则改了到期日之后
   再也收不到提醒，而系统看起来一切正常。
3. **派发前重新判定**。生成与发送之间可能隔很久，收件人可能已停用或关闭提醒、
   任务可能已完成——照着生成时的结论发出去会打扰用户。

**开发与验证中发现并修复的四个问题**（逐个记下来，避免后来者重犯）：

1. **邮件未启用被记成 `failed`**（由冒烟实测发现）：领域层对 `skipped` 的定义里
   本就写着"邮件未启用"，实现却把它算作发送失败。这是"只看单元测试不会发现"的一类
   问题——假发送器不会返回 `ErrDisabled`。已补 `TestReminderMailDisabledIsSkippedNotFailed`。
2. **`scheduled_for` 用错了日期**："到期前/开始前"提醒最初把计划发送时刻算成
   **目标日期**（到期日）的 09:00，于是提醒生成后一直卡在"计划时间未到"，
   永远发不出去。正确值是**提醒日**（今天）的 09:00——提醒是在今天发,
   而不是在到期那天发。
3. **重试用了数据库 `now()`**：`ResetForRetry` 最初把 `scheduled_for` 设为
   `now()`（库时间），与注入时钟分叉，重试后的提醒因为"计划时间在未来"而发不出去。
   改为由用例层传入注入时钟的时刻（与红线 9 同源）。
4. **冒烟脚本的前置状态**：脚本的用户资料用例会把 `reminder_enabled` 置为 `false`
   来证明"字段真的生效"，但不恢复，于是提醒用例测到的是"资格判定生效"
   而不是"调度器能生成提醒"。现在提醒用例开头显式恢复该开关——
   这类"用例之间的隐藏前置状态"是端到端脚本最容易积攒的债务。

**验证**：`TestReminderOverdueLifecycle`（生成/去重/派发/邮件内容九项/状态写回/端点）、
`TestReminderDueSoonFollowsBusinessDays`（时钟移动到周一，验证工作日规则）、
`TestReminderSkipsIneligibleRecipients`、`TestReminderFailureRecordsReasonAndCanRetry`、
`TestReminderEventKinds`、`TestReminderListScoping`、
`internal/platform/mail` 的 7 个单测（含假 SMTP 服务器上的整轮会话与"拒绝明文降级"）、
`TestReminderMailDisabledIsSkippedNotFailed`，以及 8 处变异验证（5.7 第 43–50 条）。
冒烟新增 12 项断言（含真实调度器在真实数据库上生成提醒）。

### 5.15 潜伏的测试时间炸弹：时钟混用（2026-10-11）

**现象**：本轮某次全量测试出现 **87 个用例同时失败**，而三分钟前同一棵代码树是全绿的。
失败信息是 `会话过期时间已过，拒绝写入`，所有登录返回 500。

**根因**：会话的 `ExpiresAt` 由**注入时钟**算出（harness 固定为 `2026-10-11T09:30Z`，
加 1 小时 TTL = `10:30Z`），而 `RedisSessionStore` 用 `time.Until`（**真实时钟**）
判断是否已过期。真实时间越过 `10:30Z` 的那一刻，所有新会话都被判为"已过期"。

**为什么这比一个普通缺陷更危险**：

- 它让"测试全绿"变成**取决于运行时刻**的证据。本次是 10:27Z 绿、10:32Z 红；
  换成 CI 上的任意时刻都可能复现，而排查者会先怀疑自己刚改的代码。
- 那条 TTL 断言当时**把时钟差补偿了回去**
  （`expected := TTL + harness.Clock.Now().Sub(time.Now().UTC())`），
  等于把这个缺陷写进了测试：断言通过，缺陷仍在。

**修复**：过期判定也走注入时钟（`NewRedisSessionStore` 增加 `clk` 参数），
并把 TTL 断言改成纯粹的配置量比较。修复后 87 个失败全部消失。
规则写入 [backend/docs/B01 §5.11](./B01-Go服务端架构设计.md)：任何"现在"的判断都不得直接调用
`time.Now()` / `time.Until()`；并给出了检查方法（在业务代码里搜索这两个调用）。

**教训（值得与 5.7 的变异验证并列）**：验证不仅要跑对工件，还要**与运行时刻无关**。
一条依赖墙钟的断言，其"通过"本身就不是证据。

### 5.16 全局限流（2026-10-12）

**背景**：`429 rate_limited` 从第一阶段起就登记在契约的错误码表里、映射表里也有它，
但**全仓库没有任何限流实现**——没有中间件、没有产生点。这属于"登记了但没实现"的能力：
错误码表看起来完整，实际那条分支永远不会走到。人工决策把它补上：
"简单地做一个全局中间件挂上即可，现阶段不做用户/会话级限流。"

**实现**（`internal/httpapi/ratelimit.go`）：按**连接的来源地址**分桶的令牌桶，
挂在中间件链最外层（`ErrorHandler` 之后、路由与会话网关之前），
超限返回统一信封 + `Retry-After`。配置见《B03》§3.8，契约见《S02》§2.8。

**四个刻意选择**（否则后来者很容易"顺手改回去"）：

1. **不做用户/会话级限流**。按会话限流在登录之前就失效，而登录口令尝试正是最需要挡的；
   按用户限流要先解析会话，等于把一次 Redis 往返压在限流之前。
2. **不信任 `X-Forwarded-For`**。gin 默认的 `ClientIP()` 会读该头，而它由客户端提供——
   用它分桶等于"换一个头就绕过"，得到一个看起来有防护、实际没有的假象。
   代价是：部署在反向代理之后时所有请求落到同一个桶，这被明确接受
   （本功能定位就是"全局封顶"）。
3. **默认额度刻意宽松**（3000/分钟、突发 300）。限流不应把正常使用（含 197 项冒烟）
   打成 429；它挡的是脚本化刷取。需要复现 429 时把 `ratelimit.burst` 调小。
4. **空闲桶 10 分钟后回收**。一张按来源地址增长的 map 若从不清理，就是一个慢速内存泄漏。

**验证**：`internal/httpapi/ratelimit_test.go` 的 7 个用例（突发配额与 `Retry-After`、
**用注入时钟推进时间**证明令牌按注入时钟补充、按来源分桶互不影响、空闲桶回收、
零值配置等于关闭、429 走统一信封、伪造 `X-Forwarded-For` 无法绕过），
配置层新增 2 类非法取值用例（共 17 类），并把《S02》§5 与《B04》§6 第 37 条登记为偏离。
端到端侧：限流**开启**时 `scripts/smoke.ps1` 仍 **197 项全通过**——
这证明它没有误伤正常使用；429 本身由上述单测确定性覆盖，不由冒烟制造。

**真实服务上的 429 路径复核**（2026-10-12，把 `RATELIMIT_BURST` 调成 3、速率 6/分钟，
对 `/healthz` 连发 6 次）：

```text
req 1 -> 200   req 2 -> 200   req 3 -> 200
req 4 -> 429 retry-after=10 body={"error":{"code":"rate_limited","message":"Too many requests.","request_id":"..."}}
req 5 -> 429 retry-after=10
req 6 -> 429 retry-after=10
伪造 X-Forwarded-For 后再请求 -> 429（换头不能绕过）
```

`Retry-After = 10` 与配置吻合（6/分钟 = 每 10 秒 1 个令牌），说明它给的是**真实**的等待时间
而不是一个固定值。

是否需要改代码由人工决定。它们都属于同一类风险——**契约没写、行为却已存在**，前端只能靠试。

| # | 现象（实测/读码确认） | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | **请求体里的 UUID 字段没有前置校验**：`group_id` / `user_id` / `parent_id` 传非 UUID 会直达 PG 触发 `22P02` → `500` | 客户端拼错 id 得到 500 而不是 400，前端无法区分"我传错了"与"服务端炸了" | 与路径参数一视同仁，加 `idgen.IsUUID` 前置校验 |
| 2 | **日期/时间格式非法 → `400 invalid_request`，且 `fields` 丢失**（`httpapi.Date` / `Timestamp` 的解析错误落到 `BindJSON` 兜底分支；`types.go` 里准备的 `fields.timestamp` 到不了响应） | 前端拿不到"哪个字段格式错了"；契约 §2.4 的 422 样例与实际不符 | 让自定义解析错误映射为 422 + 字段名；同时补一条集成测试（本轮实测**没有任何测试覆盖**这条路径） |
| 3 | **日期字段可省略但会写成零值 `0001-01-01` 并返回 2xx**（创建项目/任务、只改单侧日期） | 数据里出现明显错误的日期，只在展示时才发现 | 把两侧日期设为必填，或明确默认值语义 |
| 4 | **`PATCH /projects/{id}` 与 `/archive` 对"不可见项目"返回 `403`**，而成员管理端点对同类请求者返回 `404 project_not_found` | 口径不一致；403 能区分"项目存在"与"不存在"，与"不可见即不存在"的既有约定相悖 | 统一为 404 |
| 5 | **归档只读可被绕过**：`PATCH` 显式带非 `archived` 的 `status` 会跳过只读检查；带 `status: "archived"` 却不写 `archived_at`；且没有解除归档的端点 | 归档语义（只读、不可逆）不完备 | 收紧 `status` 的写入路径，或明确"归档状态只能由 `/archive` 改写" |
| 6 | **空写入会成功**：只提交 `expected_updated_at`（无可改字段）在 projects / tasks / groups 上返回 `200` 并推进版本；**Users 域拒绝** | 同一系统两套口径；空写会让别人手里的版本无谓失效 | 统一为"拒绝空更新"（Users 域已有实现可复用） |
| 7 | **任务创建者不必是项目成员**：只校验"对项目有写权限"，`group_editable` 的组内成员可直接创建并成为唯一持有者 | 与旧契约措辞（"创建者不是项目成员时会被拒绝"）不一致 | 明确取舍：要么补校验，要么把该行为写成契约 |
| 8 | **复制任务沿用源任务的 `status` / `progress` / `priority` / `is_milestone`**（只清空 `id` / `created_by` / `deleted_at` / `parent_id`） | 前端以为"复制 = 新建一个未开始的任务" | 契约写明复制字段范围（已写进 A05） |
| 9 | **幂等键的并发窗口**：唯一键在创建副本**之后**写入，并发同 key 可能 `409 conflict` 但副本已创建；重放时已删除的副本仍返回 `200` | 前端重试语义不明确 | 把键的写入并入同一事务，或在契约里写明窗口 |
| 10 | **Groups 的两处响应缺字段**：普通更新的 `membership_role` / `membership_status` 恒为 `null`（转移时反而带回新所有者）；写成员端点返回的 `username` / `display_name` / `email` 是空串 | 前端会把它当成"非成员"或渲染出空名字 | 补 JOIN 或从响应里去掉这些字段 |
| 11 | **甘特图的 `can_manage_project` 对系统管理员为 `false`**（该字段的 actor 未携带系统角色），而 `can_edit_tasks` / 逐任务 `can_edit` 对管理员照常放行 | 与"管理员对所有项目放行"（《S02》§5）存在张力 | 统一 actor 构造（`actorOf`）后重测 |
| 12 | **`POST /auth/logout` 无 Cookie 时返回 `401`**（它不在会话白名单里），而契约旧措辞是"令牌缺失或已失效仍返回成功" | "重复登出"在前端会变成错误 | 契约写明实际口径（已写进 A01），或把 logout 放进白名单 |
| 13 | **`GET /reminders` 不接受 `status` 参数**（数据层支持但未暴露）；`kind` 传非法值返回**空列表**而不是 400 | 前端以为能按状态筛选、或以为"没有提醒" | 暴露参数并做枚举校验 |
| 14 | **404 类错误不带 `fields`**（契约样例里有 `fields.project_id`） | 前端按样例取字段会拿到 undefined | 契约样例改成实际形状（api 文档已按实际写） |

> 这些条目**不改变本轮交付**：前端可以照 `docs/api/` 的实测口径先做；
> 其中 1、2、4、5、6 建议在进入前端联调前修掉，因为它们会让前端把服务端缺陷当成自己的 bug。

### 6.4 不满足即不交付的红线（承接到后续阶段）

以下条件必须持续成立，任何阶段都不得突破：

1. 不得用空路由或仅返回成功的占位实现冒充"已实现"。
2. 不得以"单元测试通过"作为交付依据；涉及 SQL 或约束的改动必须有真实数据库验证。
3. 不得在 handler 中复制权限规则或拼接 SQL。
4. 不得向客户端泄漏堆栈、SQL、物理路径或敏感值。
5. 不得引入未被使用的抽象层。
6. 归一化/校验函数接收"部分字段"结构体时，必须断言已提供的字段没有被静默丢弃
   （见 5.5 第 5 条）。
7. **不得用"并发跑一次恰好通过"充当并发正确性的证据**。并发类断言必须满足其一：
   用外部会话占住行锁等方式让交错**确定发生**，或经变异验证证明它在缺陷存在时确实失败
   （见 5.8 第 2 条）。
8. **验证必须跑在正确的对象上**。启动服务做端到端验证前，先确认端口由新构建的进程持有：
   结束后台任务不等于结束其子进程，旧二进制会继续服务请求，让"验证通过"变成
   对上一版产物的验证（见 5.8 第 3 条）。变异验证同理：先确认被测用例真的在
   所选包内被执行，否则"没有匹配用例"也会被误读成"用例没拦住"。
9. **验证必须与运行时刻无关**。断言不得依赖墙钟：任何"现在"的判断都走注入时钟
   （`clock.Clock`），业务代码里不得直接出现 `time.Now()` / `time.Until()`。
   实测代价见 5.15：时钟混用让 87 个用例在某个墙钟时刻之后必然失败，
   而三分钟前同一棵树是全绿的——**"全绿"因此不再可信**。
   同理，不要为了迁就缺陷而把补偿写进断言（当时的 TTL 断言正是如此）。

**六条最容易踩的坑**（都实际发生过）：

1. 冒烟前先确认 **8000** 端口由**新构建的进程**持有：结束后台任务不等于结束其子进程，
   旧二进制会继续服务请求，让"验证通过"变成对上一版产物的验证（见 5.8 第 3 条）。
2. 测试是否通过**不得取决于运行时刻**（见 5.15）。
3. 重跑冒烟前注意它会创建数据；脚本自身幂等（用户名带时间戳），无需清理。
4. **冒烟必须与服务同配方**：脚本对"调度器已生成提醒"只轮询 30 秒，而
   `config.toml` 的 `scheduler.interval_seconds` 是 60 → 得到 `201 通过 / 1 失败`。
   `docker/config.test.toml` 则是另一种不匹配（`scheduler.enabled = false`、
   `mail` 指向 Mailpit，而脚本断言的是"邮件未启用 → skipped"），同样不能用。
   两条路径都在 2026-10-12 实测复现过，属**配置不匹配**而非功能缺陷。
5. **Makefile 的 recipe 必须是单个物理行**：本 Makefile 没有 `.ONESHELL`，GNU make 默认
   **为每条 recipe 行单独起一个 shell**，因此用行尾反引号拼出的多行 `$env:` 赋值不会存活到
   `go run` / `go test` 那一行。实测：把一个"以反引号结尾、后面没有内容"的命令交给
   `pwsh -Command`，它以 1 退出，整条目标随即失败——`run-test-config` 与 `test-integration`
   原先都是这种写法，已合并为单行（新增变量时继续接在同一行里）。
6. **本机 `make` 仍不能直接跑带 `$env:` 的 recipe**（2026-10-21 实测）：Windows 上 GNU make
   默认用 cmd 执行 recipe，`migrate-test-up` / `run-test-config` 会报
   “The filename, directory name, or volume label syntax is incorrect.”。请改用 pwsh 直接执行
   等价命令；另外冒烟还要求 `SECURITY_REGISTRATION_REQUIRES_APPROVAL=false`，
   否则注册用户停在 `pending`，登录 401（实测 141 项失败）。
