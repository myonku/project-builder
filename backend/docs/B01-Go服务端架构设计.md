## 2. 技术选型

早期实现的功能骨架是完整的，但框架层存在持续性的摩擦成本。实测确认的问题包括：

| 问题 | 实测证据 |
| --- | --- |
| 框架在 `Optional[Annotated[...]]` 上无限递归 | `lihil/utils/typing.py:282` 自我递归，应用**无法启动** |
| 校验元数据对 JSON body 静默失效 | `Annotated[int, Param(gt=0, le=100)]` 被 msgspec 忽略，`page_size=9999` 与 `page=0` 均通过 |
| 框架错误绕过自定义错误契约 | 未注册求解器的异常在 `routing.py:224` 直接 `raise`，输出纯文本 500 与 RFC7807，与文档契约不一致 |
| 异步 ORM 的隐式 IO 难以察觉 | 更新后访问 `updated_at` 触发同步重载 → `MissingGreenlet`，**所有更新/删除端点 500**，单元测试完全无法发现 |

Go 侧的对应收益是明确的：编译期类型检查、稳定的 httptest 测试模型、成熟且行为可预测的
Gin/pgx 生态。但必须同时承认：**更换语言不会自动修复逻辑缺陷**。原实现中
`owner_id + assignee_id` 双条件 JOIN 恒空、版本校验"先读后写"、逻辑删除过滤不一致，
都是与语言无关的逻辑错误，照搬到 Go 会原样复现。因此第 5 节把每一个已确认缺陷都转成了
必须覆盖的测试用例。

## 4. 分层设计（有意收敛，不做 1:1 平移）

### 4.1 早期分层的问题

原布局有 8 个平行子包，一次请求要穿过
`struct → domain → core → modules/*/repository(Protocol) → infrastructure/database/repositories`
五层，其中 Protocol 与实现、`struct/repositories` 记录对象与 ORM 实体、`factory/factory.py`
的工厂函数都属于"为可替换性付出、但从未真正替换"的间接层。Go 版本保留**有实际收益**的边界，
删除只为对称而存在的层。

### 4.2 目标目录结构

> 树根是**仓库根**。2026-10-13 起服务端整体位于 `backend/`（Go 模块根），
> 前后端共用的《S01》《S02》在仓库根 `docs/`；下面是服务端自己的结构。

```text
project-builder/                  # 仓库根
├── docs/                         # 前后端共用文档（00 需求、04 接口契约）
├── frontend/                     # 前端工程（规划中）
└── backend/                      # Go 服务端（Go 模块根，命令都在这里执行）
    ├── cmd/api/main.go           # 唯一入口：装配依赖、启动 HTTP、优雅关闭
    ├── internal/
    │   ├── config/config.go      # 启动时读取一次，返回不可变配置
    │   ├── platform/             # 基础设施（原 infrastructure/）
    │   │   ├── postgres.go       # pgxpool 创建与健康检查
    │   │   ├── redis.go          # Redis 客户端
    │   │   ├── mail/             # 邮件发送接口 + SMTP/Mailpit 实现
    │   │   ├── storage/          # 文件存储接口 + 本地实现
    │   │   └── clock/            # 可注入时钟
    │   ├── domain/               # 纯业务规则：无 IO、无 SQL、无 HTTP
    │   │   ├── user.go
    │   │   ├── group.go
    │   │   ├── project.go
    │   │   ├── task.go
    │   │   ├── permission.go
    │   │   └── errors.go         # 领域错误类型（含错误码语义）
    │   ├── app/                  # 业务模块：用例编排 + SQL 访问 + 错误映射
    │   │   ├── auth/
    │   │   │   ├── service.go    # 用例逻辑与权限编排
    │   │   │   ├── repo.go       # 该模块的 SQL（sqlc 或手写 pgx）
    │   │   │   └── http.go       # 路由、绑定、响应
    │   │   ├── users/  groups/  projects/  tasks/
    │   │   └── attachments/  reminders/  audit/  planviews/
    │   ├── httpapi/              # 跨模块 HTTP 关注点
    │   │   ├── router.go         # 路由装配
    │   │   ├── middleware/       # requestID、session gateway、限流、恢复
    │   │   ├── response.go       # 统一 data/pagination 响应
    │   │   └── problem.go        # 统一错误信封与领域错误→HTTP 映射
    │   └── database/migrations/  # 版本化 SQL 迁移
    ├── docs/                     # 服务端文档（01/02/03/05/06；00/04 在仓库根 docs/）
    ├── docker/                   # 测试依赖 compose（Postgres/Redis/Mailpit）
    └── Makefile                  # run/test/migrate/lint
```

### 4.3 依赖方向（单向）

```text
cmd/api  →  httpapi  →  app/*  →  domain
                ↓         ↓
             platform  ←──┘   （app 可用 platform 的接口，domain 不可用任何东西）
```

- `domain` **只允许**依赖标准库。规则是纯函数，便于表驱动测试。
- `app/*` 负责用例、权限编排、事务边界与 SQL。
- `httpapi` 负责绑定、序列化、状态码与错误信封。
- `platform` 提供外部资源，由 `main` 创建并注入。

### 4.4 相对原设计的具体收敛

| 早期结构 | 现在的结构 | 理由 |
| --- | --- | --- |
| `struct/api/*` + `struct/repositories/*` + `core/` | `httpapi/response.go`、`problem.go`、各模块 `repo.go` 的入参/出参结构 | 减少三层纯数据搬运；Go 结构体可同时承担传输与持久化出参 |
| `modules/*/repository.py` Protocol + `infrastructure/.../repositories/*.py` 实现 | 每模块一个 `repo.go` | 从未发生过替换；接口只在测试需要替身时才定义，且定义在消费方 |
| `factory/factory.py` 依赖工厂 | `main.go` 显式装配 + 各模块构造函数 | 装配点透明，避免反射式 DI |
| `infrastructure/runtime.py` | `platform` + `main.go` 生命周期 | Go 无异步生命周期钩子需求 |
| `api/errors.py` + `core/errors.py` 双层错误 | `domain/errors.go` + `httpapi/problem.go` | 错误语义在领域，映射在 HTTP |

**保留的边界（必须继续遵守）**：
- ORM/数据库类型不得出现在 HTTP 响应结构中。
- 权限与领域规则只能在 `domain` / `app` 中判定，不得在 handler 里复制。
- 时间统一 UTC 存储，业务日期按用户时区计算。

## 5. 必须规避的历史缺陷（核心资产）

下列每一条都在早期实现中被实测确认。实现时必须**修复并配套测试**，
否则重写就是纯粹的返工。

### 5.1 更新路径不得读"过期实体"

- 现象：写操作返回 500；根因是事务提交/刷新后实体属性被标记过期，读取触发隐式 IO。
- Go 的正确做法：更新语句使用 `UPDATE ... RETURNING updated_at`，或显式 `SELECT` 回读；
  绝不依赖"内存对象里可能过期的字段"。
- 规避手段：Go 的 `struct` 是值拷贝，天然不会出现该问题，但**仍需**保证
  `updated_at` 由数据库生成且被真实回读。

### 5.2 版本冲突必须是原子比较并交换（CAS）

- 原缺陷：先 `SELECT` 比较 `expected_updated_at`，再无条件 `UPDATE`，并发下两个请求都能通过。
- 正确做法：把版本条件放进写语句本身：

```sql
UPDATE projects
   SET name = $1, updated_at = now()
 WHERE id = $2 AND updated_at = $3
RETURNING id, updated_at;
```

`RowsAffected() == 0` 时再区分"不存在"与"版本冲突"（补一次存在性查询）。

### 5.3 多条件组合筛选不得共用一个 JOIN

- 原缺陷：`owner_id` 与 `assignee_id` 同时给出时，两个谓词落在同一张成员表的同一行，
  要求同一个人既是 owner 又是 assignee，结果恒为空（实测：单条件各返回 1 条，组合返回 0 条）。
- 正确做法：**每个成员条件各用一个别名 JOIN**：

```sql
SELECT t.* FROM tasks t
  JOIN task_members mo ON mo.task_id = t.id AND mo.role = 'owner' AND mo.user_id = $1
  JOIN task_members ma ON ma.task_id = t.id AND ma.user_id = $2
 WHERE t.project_id = $3 AND t.deleted_at IS NULL;
```

### 5.4 列表分页与排序

- 分页必须在 SQL 层 `LIMIT/OFFSET`，不得全量载入内存后切片。
- `page >= 1`、`1 <= page_size <= 100` 必须由服务端校验并返回 400 `invalid_request`。
- 排序字段必须白名单校验，未知字段返回 400。
- 排序必须带 `id` 作为次级键，否则等值键在翻页时可能重复或漏出。

### 5.5 逻辑删除过滤必须一致

- 原缺陷：列表查询过滤了 `deleted_at IS NULL`，但按 ID 单查没有过滤，导致已删除任务仍可读取。
- 正确做法：把"默认排除已删除"作为仓储层的默认行为，单查与列表走同一套条件；
  仅在显式 `include_deleted` 时放开。

### 5.6 幂等键必须持久化并带唯一约束

- 原缺陷：`Idempotency-Key` 完全未实现，同一 key 连续两次 copy 产生两个任务（实测确认）。
- 正确做法：`idempotency_keys` 表 + `UNIQUE(user_id, scope, idempotency_key)`；
  先查后写，并在插入冲突时将整个事务判定为重复请求（或返回已存结果）。
- 幂等键作用域必须包含用户与操作，避免跨用户串用。

### 5.7 错误映射必须集中且完整

- 原缺陷：领域错误全是裸 `ValueError`，未注册映射 → 全部 500。
- 正确做法：`domain/errors.go` 定义带语义的错误类型，`httpapi/problem.go`
  用一处映射表转换为状态码与错误码，并覆盖框架自身的绑定/校验错误。
- 兜底：未识别错误统一 500 `internal_error`，**不得**向客户端泄漏堆栈或 SQL。

### 5.8 单一持有者约束应由数据库保证

- 已有正确实践（保留）：`project_members`、`task_members` 使用 PostgreSQL 部分唯一索引
  `UNIQUE (parent_id) WHERE role = 'owner'`。
- `groups.owner_id` 的处置**已决策（2026-10-11）**：不补循环复合外键。
  工作组所有权是 `groups` 自身的单值列，`owner_id` 天然唯一；成员关系由 `group_members` 表达。
  两者的一致性改由"单一写路径 + 应用层拒绝降级 + 回归测试"保障。
  完整理由（含放弃复合外键的三条原因）见《B02-数据库模型与迁移.md》§3.2.1。
- **约束**：Groups 阶段实现时不得把该划分改为复合外键，除非同时给出迁移与回滚方案。
- **转移**：唯一持有者必须可转移，见 5.10；工作组所有权的转移语义另见
  《B02-数据库模型与迁移.md》§3.2.1（`groups.owner_id` 与 `group_members` 的 manager 行
  必须同事务改写）。

### 5.9 权限判定必须显式处理系统管理员（新增，2026-10-11）

**规则：业务中的每一处权限校验都必须允许对系统管理员放行。**
需求文档 4.1 规定系统管理员"管理所有用户、工作组和系统级数据，处理异常数据"，
因此任何"能否看到 / 能否操作"的判定都要把管理员视为通过。

**放行的边界（同样必须遵守）**：

| 类别 | 管理员是否放行 | 例子 |
| --- | --- | --- |
| 权限判定（能否看到 / 能否操作） | ✅ 放行 | 项目/任务/工作组的可见性、成员管理、所有权转移 |
| 状态规则 | ❌ 不放行 | 归档项目只读（对管理员同样只读） |
| 领域不变式 | ❌ 不放行 | 唯一持有者不可降级/移除、唯一管理员不可降级、任务成员必须是项目成员 |
| 字段与取值校验 | ❌ 不放行 | 名称长度、日期区间、枚举取值 |

**两个必须避免的实现方式**（都实际发生过）：

1. **把角色丢掉**。权限函数接收的是 `domain.User`，而用例层手上常常只有 `actorID`；
   随手写 `domain.User{ID: actorID}` 会让 `SystemRole` 恒为空，
   于是"管理员放行"的代码写了却永远不生效，且**没有任何报错**——
   表现为管理员被当成普通成员。正确做法是由查询一并取出调用者的系统角色
   （各模块记录上的 `ActorSystemRole` 字段 + `actorOf()` 重建），
   或者把完整的 `domain.User` 一路传下去。
2. **只改领域层或只改 SQL**。读路径的可见性由 SQL 谓词决定（不是成员就查不到该行），
   写路径的权限由领域函数决定。两者必须同时放行，否则会出现
   "管理员能改却看不到"或"能看却改不了"的半截状态。

**不适用放行的两类判断**（不要把规则扩大化）：

- **视图定义**：个人计划视图 = "我参与的项目"，这是视图的定义而不是权限门槛，
  因此管理员看到的仍然是**自己的**个人视图。同理"当前用户所属工作组"这类
  以归属为定义的集合，是否对管理员放开由该端点的契约决定（本项目对列表放开，
  因为管理员需要靠它找到要处理的对象）。
- **数据归属**：例如"只能转移给自己拥有的对象的持有者身份"这类语义，
  不属于权限校验。

**判定顺序**：管理员放行必须放在**其它条件之前**。反例：若先判断"工作组是否启用"
再判断是否管理员，则一个被停用的工作组连管理员都改不了，也就没人能重新启用它——
管理员兜底的意义正在于此。

**为什么必须写成规则**：这类缺陷不会以 500 或错误码的形式出现，只会让一个本应可用的
兜底手段静默失效。持有者离职或被停用后，所有权转移是唯一的补救路径；
如果它对管理员也不可用，系统就没有任何受支持的补救方式了
（见《B05-进度与验证记录.md》5.12）。

### 5.10 所有权必须可以转移（新增，2026-10-11）

任何"唯一持有者"（项目的 owner、任务的 owner、工作组的所有者）都必须有**转移**路径，
且转移必须在同一事务内完成"先降现任、再升目标"：

- 只降不升 → 留下"没有持有者"的不可用状态；
- 只升不降 → 撞上部分唯一索引（第二个持有者）；
- 反过来先升后降 → 同样撞上唯一索引。

单条 SQL 无法同时满足"至多一个"（索引）与"至少一个"（事务），
因此不允许出现"先降级再提升"两步式 API——两步之间的中间态无人可管理。
这条规则与 5.8（单一持有者由数据库保证）是同一件事的两面。

### 5.11 时间只有一个来源：注入的时钟（新增，2026-10-11）

**规则：任何"现在是什么时候"的判断都必须走注入的 `clock.Clock`，不得直接调用
`time.Now()` / `time.Until()`。** 会话过期、提醒计划时间、工作日推算、逾期判定
全都属于这一类。

理由不是风格，而是**一致性**：如果一个值由注入时钟算出、却由真实时钟判断，
两个时钟一旦不一致（测试里的固定时钟、部署中的时钟漂移、容器与宿主时间不同步），
行为就会自相矛盾。本仓库实测到的后果是：

- 会话的 `ExpiresAt` 由固定时钟算出（`2026-10-11T09:30Z` + 1 小时 = `10:30Z`），
  而存储层用 `time.Until`（真实时钟）判断"是否已过期"。真实时间越过 `10:30Z`
  的那一刻起，**所有登录返回 500**：87 个用例同时失败，
  而三分钟前同一棵树是全绿的。
- 更糟的是那条 TTL 断言当时**把时钟差补偿了回去**，等于把这个缺陷写进了测试：
  断言通过，缺陷仍在。

**测试是否通过取决于运行时刻**，比一个普通缺陷更危险——它让"全绿"不再可信。
因此时钟混用按红线处理。

**检查方法**：在业务代码里搜索 `time.Now()` 与 `time.Until()`；
除 `internal/platform/clock` 的实现本身以及"日志时间戳"外，都不应出现。

### 5.12 邮件与外部副作用：接口隔离 + 不阻塞请求（新增，2026-10-11）

- 发送通道只以接口形式进入业务层（`mail.Sender`），实现由装配点注入。
  于是测试用替身即可验证全部逻辑，换供应商只换实现。
- **未启用的发送器必须返回错误**，不能静默成功：否则"没配邮件"会被记成"已发送"，
  那是比失败更糟的假象。业务层把该错误映射为 `skipped` 而不是 `failed`——
  它是配置状态，不是这条记录的失败。
- 任何外部副作用（SMTP、将来可能的 Webhook）都不得出现在请求路径上：
  请求路径只允许**插入一行**记录，发送交给后台循环。
  需求文档 §9 明确要求"邮件发送不得阻塞用户操作"。
- 副作用失败**不回滚主操作**：任务已经写库成功，因为一封提醒没排上队就回滚它，
  是把次要功能的失败放大成主要功能的失败。

## 6. 请求与事务边界

```text
HTTP 请求
  → requestID / 恢复中间件
  → session gateway（仅检查 Cookie 存在性）
  → 绑定与字段校验（绑定失败 → 422 validation_error）
  → 用例服务：对象存在性 → 可见性 → 权限
  → expected_updated_at / Idempotency-Key
  → 领域规则（纯函数）
  → 事务写入（CAS 更新 + RETURNING）
  → 提交后：审计 / 提醒 / 文件处理
  → 统一成功或错误响应
```

约束：

- 核心数据提交前不得发送邮件、生成提醒或执行不可撤销的外部文件操作。
- Session gateway 只检查 Cookie 存在性；会话有效性由 Redis 会话存储判定。
- 公开路径由中间件白名单维护，业务 handler 仍需自行校验当前用户。

## 7. 配置与运行

- 配置**只在启动时读取一次**，解析校验后成为不可变对象注入各模块。
- 优先级：代码默认值 < TOML < 环境变量。
- 敏感值（数据库密码、SMTP 凭据、会话密钥）不得进入仓库；提供脱敏的 `.env.example`。
- 启动失败必须快速失败并给出脱敏后的字段名与原因。
- 详细键名见《配置与运行》。

## 8. 测试策略

| 层次 | 范围 | 依赖 |
| --- | --- | --- |
| 领域单元测试 | `internal/domain` 全部规则，表驱动 | 无 |
| 用例测试 | 用仓储替身覆盖权限、状态流转、跨对象校验 | 替身 |
| **集成测试** | 真实 PostgreSQL + Redis，覆盖 SQL、约束、事务、CAS、并发 | Docker |
| HTTP 测试 | `httptest` 覆盖状态码、信封、分页、错误码 | 依赖可注入 |
| 端到端 | 完整业务流程串联 | 全部 |

**关键教训**：早期实现的 45 个单元测试全部通过，却完全没有发现
"所有更新/删除端点 500"，因为测试用替身替换掉了真正出错的那一层。
因此 Go 版本**必须**把集成测试作为常规测试的一部分，而不是可选项；
每一条 SQL 查询、每一个数据库约束都应有真实数据库上的验证。

## 9. 变更规则

1. 新增模块前必须明确：数据对象、权限边界、状态转换、时间语义、错误处理、日志、测试范围。
2. 任何涉及数据结构、公共接口、配置格式或安全边界的变更，同步更新 `docs/` 下对应文档。
3. 不得通过 handler 层快捷逻辑绕过 `domain` 规则或直接拼接 SQL。
4. 不得为"未来可能需要"引入未被使用的抽象层。
