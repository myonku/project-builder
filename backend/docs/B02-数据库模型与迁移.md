# 数据库模型与迁移

## 1. 文档定位

本文档是数据库结构的权威来源，全部内容**已在真实 PostgreSQL 16 上验证通过**
的迁移文件逐字提取而来（验证方式：空库执行全部迁移、模型与迁移 autogenerate 零漂移、
约束实际生效测试）。Go 版本的 SQL 迁移应以本文档为准。

> **2026-10-20/21 规划（部分落地）**：`attachments.storage_backend` 迁移账本已落地（head 6 → 7）；
> `users` 头像 4 列已由 `000008` 落地（head 7 → 8）；
> `session_version`、`password_reset_states` / `password_reset_tokens` 仍计划在 `000009`（落地后 head 9）。
> MongoDB GridFS 只存字节，不属于 PostgreSQL schema。
> 评估与阶段顺序见 [P01](../../docs/P01-Worklane-规划-2026-10-20.md)。

## 2. 通用约定

- 所有业务表主键为 `UUID`，使用 **UUIDv7** 生成（时间有序）。
- 所有业务表包含 `id`、`created_at`、`updated_at`。
- 瞬时时间列统一 `TIMESTAMPTZ`，存储 UTC。
- 业务日期列使用 `DATE`（不含时分秒）。
- 表名与字段名使用 `snake_case`，表名复数。
- 枚举值使用稳定英文机器值，并用 `CHECK` 约束保护。
- 需要保留历史的数据使用逻辑删除（`deleted_at`），查询默认排除。

`created_at` / `updated_at` 的数据库默认值与更新语义：

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

> **重要**：早期实现把 `updated_at` 的更新放在 ORM 层（`onupdate=now()`），
> 数据库没有 `ON UPDATE` 触发器。Go 版本应在每条写语句中显式 `SET updated_at = now()`，
> 或统一加触发器。无论选择哪种，都必须保证 `updated_at` **真实推进**且有测试覆盖，
> 因为客户端的 `expected_updated_at` 版本协议完全依赖它。

### 3.2 `groups`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |
| `name` | VARCHAR(160) | NOT NULL |
| `description` | VARCHAR(2000) | NULL |
| `status` | VARCHAR(16) | NOT NULL, DEFAULT `'active'`, CHECK `IN ('active','disabled')` |
| `owner_id` | UUID | NOT NULL, FK → `users.id` ON DELETE RESTRICT |

> **所有者语义的决策（2026-10-11 确定）**：
> `groups.owner_id` 是普通外键 + NOT NULL。工作组的所有权**不是**"成员表里的一个角色"，
> 而是工作组自身的一个治理属性；`group_members` 表达的是"谁参与了哪个组"。
> 因此不引入 `groups.owner_id ↔ group_members.role='manager'` 的循环复合外键，
> 改为采用"单一写路径 + 应用层拒绝降级 + 回归测试"三重保障，详见 §3.2.1。

#### 3.2.1 所有权不变式的落地方式

**问题**：`projects` / `tasks` 用部分唯一索引保证了"最多一个 owner"，而 `groups` 没有
等价的数据库约束。"一个工作组只有一个所有者"目前只由 `owner_id` 是单值列这一点隐含保证。

**决策：不引入循环外键。** 备选方案是把 `(id, owner_id)` 复合外键指向
`group_members(group_id, user_id) WHERE role='manager'`，用数据库强制"所有者必须是活跃组管理员"。

放弃该方案的理由：

1. **会形成循环依赖**：`group_members.group_id` 已经外键指向 `groups.id`，
   再加一条 `groups → group_members` 的外键使两表互相依赖，插入顺序需要 `DEFERRABLE`
   约束或两阶段写入，迁移与回滚都会变复杂。
2. **语义被绑死**：强制复合外键后，"所有者"就必须同时是 `group_members` 中
   `role='manager'` 且 `status='active'` 的行。而 `status` 会在"移除成员"时变为 `removed`，
   于是要么禁止移除所有者（应用层规则被硬编码进 schema），要么所有者行会被意外删除。
   需求文档 §5.2 明确"成员移除后，个人数据保留"，两者会互相冲突。
3. **存在信息重复**：`groups.owner_id` 与 `group_members.role='manager'` 会成为同一事实的
   两份表示，必须靠触发器或应用层保持同步。本项目已明确不走触发器路线
   （见《B03-配置与运行.md》第 6 节对 `updated_at` 的同类决策）。

**替代保障（三重）**：

| # | 保障 | 落地位置 | 验证方式 |
| --- | --- | --- | --- |
| 1 | 单一写路径：创建工作组时在**同一事务**内写入 `groups.owner_id` 并插入 `group_members(owner_id, role='manager', status='active')` | Groups 阶段 `app/groups/repo.go` | 集成测试断言两者同时存在或同时不存在 |
| 2 | 应用层拒绝降级：不允许移除所有者、不允许把所有者降为 `member`、不允许同一组出现第二个 `manager` 之外的治理冲突 | Groups 阶段 `app/groups/service.go` + `domain/permission.go` | 表驱动用例覆盖"移除所有者"、"降级所有者" |
| 3 | 数据库保证"一个组只有一条 `groups` 行"，因此 `owner_id` 天然唯一 | 既有 `pk_groups` | 已由迁移测试覆盖 |

**2026-10-11 补充：所有权转移**。`groups.owner_id` 可以变更，由
`PATCH /groups/{group_id}` 的 `owner_id` 字段触发。写入在**同一事务**内完成两件事：

1. `UPDATE groups SET owner_id = <新所有者>`；
2. 把新所有者对应的 `group_members` 行置为 `role='manager', status='active'`，
   并把原所有者的 manager 行降为 `member`（交出管理权）。

第 2 步是必须的：本节要求"所有者必须是活跃组管理员"，
`owner_id` 与成员行是同一事实的两种表示，分开写会静默不一致——
"所有者但没有 manager 行"会让所有者看不到自己的组、也管不了它。
实现见 `groups.Repository.TransferOwnership`。

**结论**：本项不构成数据库层的缺陷，而是"所有权归 `groups`、成员关系归 `group_members`"
这一语义划分的必然结果。该划分在 §3.2.1 固定，Groups 阶段实现时不得改为复合外键，
除非同时给出迁移与回滚方案并更新本节。

> 附带说明：**不存在**"一个用户只能拥有一个工作组"的约束，也不需要。
> 需求文档 §4.1 允许一个用户加入多个工作组，自然也应允许拥有多个工作组。

### 3.2.5 `attachments`（迁移 000003）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |
| `project_id` | UUID | NULL，FK → `projects(id)` ON DELETE CASCADE |
| `task_id` | UUID | NULL，FK → `tasks(id)` ON DELETE CASCADE |
| `uploader_id` | UUID | NOT NULL，FK → `users(id)` ON DELETE RESTRICT |
| `original_name` | VARCHAR(255) | NOT NULL，展示用原始文件名 |
| `stored_key` | VARCHAR(512) | NOT NULL，UNIQUE，存储标识 |
| `extension` | VARCHAR(32) | NOT NULL，小写含点号 |
| `size_bytes` | BIGINT | NOT NULL，CHECK >= 0 |
| `mime_type` | VARCHAR(160) | NOT NULL DEFAULT `''` |
| `storage_backend` | VARCHAR(16) | NOT NULL DEFAULT `'local'`，CHECK `IN ('local','gridfs')`；000007 |
| `deleted_at` | TIMESTAMPTZ | NULL，逻辑删除 |

约束与索引：

- `ck_attachments_single_container`：`project_id` 与 `task_id` **恰有一个非空**。
  允许同时为空或同时非空，会让"这个附件属于谁"变成运行期才知道的事，
  而权限判定完全依赖它。
- `uq_attachments_stored_key`：两行指向同一个对象是不可恢复的状态
  （任何一方被彻底删除，另一方就读到空洞）。
- `ix_attachments_project_id` / `ix_attachments_task_id`：**部分索引**，只索引
  `deleted_at IS NULL` 的行——列表默认只看未删除的。
- `ix_attachments_uploader_id`：配额检查按上传者统计。
- `ix_attachments_storage_backend`：迁移/校验工具按后端统计（000007）。

**为什么"每用户 1000 份"与"扩展名白名单"不写进 schema**：两者都是可配置项，
写进 CHECK 会让"调整配置"变成"改 schema"。它们由应用层强制，
取值来自 `[storage]`（见 backend/docs/B03）。

**为什么不用回收站表或过期清理任务**：已与人工确认——收益有限、工作量明显更大。
逻辑删除用与其它业务表一致的 `deleted_at`，需要回收磁盘时用"彻底删除"。
"彻底删除"先删对象、再删行：两种失败模式里，"对象没了行还在"可修复
（删除是幂等的），"行没了对象还在"不可见且永远占着磁盘。

**回退性质（`000003` down）**：`DROP TABLE attachments` 只删元数据，磁盘上的对象
不会随之消失（`stored_key` 随行一起没了，也就再没有记录指向它们）。因此这是**有损回退**：
需要回收空间时，应先用"彻底删除"清掉附件，再回退迁移。

> **000007 已落地（2026-10-21）**：`storage_backend` 是迁移账本，记录每行字节当前在 local 还是 GridFS，
> **不参与读路由**；`stored_key` 仍是唯一权威标识。切到 gridfs 后由 `cmd/storage-migrate` 逐行 copy 并更新。
> 旧本地文件迁移、校验、反向回滚与备份顺序见 [P01](../../docs/P01-Worklane-规划-2026-10-20.md) §3。

## 4. 迁移历史与本轮修正

迁移链的起点是**一组干净的初始迁移**：`000001_init` 直接按最终形态建表
（9 张业务表 + 全部约束与部分唯一索引），不保留"先建再改"的历史演进痕迹
（例如"先建成不带时区、再加一次迁移改成带时区"）。理由：
项目尚未部署，不存在兼容负担；从零开始按目标形态建表，
后来者读到的 schema 就是设计意图本身，而不是若干次修正的叠加。

此后每一次 schema 变化都是一个**独立编号、可双向回退**的增量迁移，
单一 head，见 §3.10 的迁移链。

### 3.2.6 `reminders`（迁移 000004）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |
| `task_id` | UUID | NOT NULL，FK → `tasks(id)` ON DELETE CASCADE |
| `recipient_id` | UUID | NOT NULL，FK → `users(id)` ON DELETE RESTRICT |
| `recipient_email` | VARCHAR(320) | NOT NULL，发送时刻的地址快照 |
| `kind` | VARCHAR(32) | NOT NULL |
| `scheduled_for` | TIMESTAMPTZ | NOT NULL，计划发送时刻 |
| `status` | VARCHAR(16) | NOT NULL DEFAULT `pending`，CHECK 四值 |
| `dedupe_key` | VARCHAR(255) | NOT NULL，**UNIQUE** |
| `attempts` | INTEGER | NOT NULL DEFAULT 0，CHECK >= 0 |
| `last_error` | TEXT | NOT NULL DEFAULT `'` |
| `sent_at` | TIMESTAMPTZ | NULL |

要点：

- **一行即"提醒记录"，不是队列**：需求 5.7 要求记录发送结果、失败原因与重试次数，
  因此这些字段就在同一行，不另建队列表。
- **`dedupe_key` 唯一约束是幂等的唯一可靠实现**：生成侧 `INSERT ... ON CONFLICT DO NOTHING`，
  于是"周期性扫描"这种必然重复运行的机制不需要任何额外去重逻辑。
  键必须含**时间窗口**（如到期日），否则改了到期日之后再也收不到提醒。
- **`recipient_email` 是快照**：用户之后改邮箱，历史记录仍应显示当时发到了哪里。
- `ix_reminders_dispatch` 是**部分索引**（只覆盖 `status = 'pending'`），供派发扫描使用。
- down 为无损回退：提醒是纯派生产物，可由任务状态重新生成。

| `actor_id` | UUID | NOT NULL，FK → `users(id)` ON DELETE RESTRICT |
| `action` | VARCHAR(32) | NOT NULL，CHECK 16 值（见下） |
| `object_type` | VARCHAR(16) | NOT NULL，CHECK 6 值（见下） |
| `object_id` | UUID | NOT NULL，**不建外键**（见下） |
| `changes` | JSONB | NOT NULL DEFAULT `'{}'`，"字段名 → 新值"的扁平摘要 |
| `request_id` | VARCHAR(64) | NOT NULL DEFAULT `''` |

枚举（与 `domain` 常量、《A09》 三处一致，由
`TestAuditEnumWhitelistMatchesDatabaseCheck` 在真实库上比对 CHECK 定义）：

- `object_type`：`user` / `group` / `project` / `task` / `attachment` / `reminder`
- `action`：`created` / `updated` / `archived` / `deleted` / `purged` /
  `member_added` / `member_role_changed` / `member_removed` /
  `owner_transferred` / `join_request_reviewed` / `shared` /
  `password_reset` / `disabled`（13 个）

> 提醒的**发送结果**不写入本表：后台派发没有操作人，而 `actor_id` 是必填外键；
> 结果记在 `reminders` 表（§3.2.6）。人工重试有操作人，记 `updated`。

索引与用途：

| 索引 | 服务的查询 |
| --- | --- |
| `ix_activity_logs_object (object_type, object_id, created_at DESC)` | "这个对象上发生过什么"（主查询） |
| `ix_activity_logs_actor (actor_id, created_at DESC)` | "这个人做过什么" |
| `ix_activity_logs_action (action, created_at DESC)` | "最近有哪些删除/转移"这类按动作排查 |
| `ix_activity_logs_created_at (created_at DESC)` | 纯时间范围查询（默认排序） |

**四个需要解释理由的选择**：

1. **一行即一条记录，append-only**：审计没有"更新"语义，因此没有 `deleted_at`，
   也只提供查询端点。记录与业务写入**同事务**（《A09》），业务回滚则这行也不存在。
2. **`object_id` 不建外键**。成员变更记在**容器对象**上（容器可以是工作组/项目/任务），
   而对象本身可能被彻底删除（附件）或逻辑删除；若加外键，审计会阻止合法删除，
   或者随级联删除一起消失——两者都与"审计"的目的相悖。
   `actor_id` 保留外键：用户在本系统里一律停用、不物理删除。
3. **`changes` 只存新值、只存白名单键**：需求只要求"关键变更内容"，
   不要求完整前后对照；完整前后值会把密码、令牌、邮件正文一类内容带进这张表。
   键名命中敏感特征的（password/token/secret/body/content/file…）在入库前
   已被替换为 `[redacted]`（领域层 `SanitizeAuditChanges`，有单测与集成测试）。
4. **不做自动清理**：内部小组规模下增长可忽略，而"日志被自动删掉"是不可逆的损失
   （人工决策 2026-10-12）。

**回退性质（`000005` down）**：**有损**，而且是本项目里损失最明确的一次——
审计记录是唯一的历史，没有任何业务表能重新推导出它（`tasks.updated_by` 只是
"最后修改人"这一个指针）。回退前应当先导出这张表。

### 3.2.8 `registration_requests`（迁移 000006）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | UUID | PK |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |
| `username` | VARCHAR(64) | NOT NULL；pending 时 `lower(username)` 唯一 |
| `email` | VARCHAR(320) | NOT NULL；pending 时 `lower(email)` 唯一 |
| `display_name` | VARCHAR(128) | NOT NULL |
| `password_hash` | VARCHAR(512) | NOT NULL，Argon2 摘要；**永不返回** |
| `timezone` | VARCHAR(64) | NOT NULL DEFAULT `UTC` |
| `status` | VARCHAR(16) | NOT NULL DEFAULT `pending`，CHECK `pending` / `approved` / `rejected` |
| `reviewed_by` | UUID | NULL，FK → `users(id)` ON DELETE RESTRICT |
| `reviewed_at` | TIMESTAMPTZ | NULL |
| `rejection_reason` | VARCHAR(2000) | NULL |

**为什么是独立表而不是给 `users.status` 加 `pending`**：

- pending 申请不是账号：不能登录、不占用户列表、不需要维护 `last_login_at`；
- 拒绝不需要伪造一个 `disabled` 用户，也不需要占用 `users` 的用户名/邮箱唯一索引；
- 审核通过时在同一事务里把申请行标记为 `approved` 并插入 `users`，两步不可分；
- `password_hash` 只在申请里保存摘要，审核时直接复用，不保存明文、不要求用户重填。

部分唯一索引只约束 `status='pending'`，因此被拒绝后可以重新申请；
并发提交相同申请时由数据库兜底为 `409`。回退 `000006` 会丢失未审核/已拒绝申请，
已通过的账号不受影响。

### 3.2.9 规划的密码重置表（迁移 000009，未落地）

**`password_reset_states`**（每用户一行）：`id` UUID PK、`user_id` UUID UNIQUE FK users ON DELETE CASCADE、
`last_self_service_reset_at` TIMESTAMPTZ NULL、`created_at`/`updated_at`。
`last_self_service_reset_at` 只由自助成功写，管理员重置不写。

**`password_reset_tokens`**（每次签发一行）：`id` UUID PK、`user_id` UUID FK users ON DELETE CASCADE、
`token_hash` VARCHAR(64) UNIQUE（SHA-256 hex）、`requested_at`、`expires_at`（CHECK > requested_at）、
`consumed_at`、`sent_at`、`failed_at`、`last_error` VARCHAR(500)、`created_at`/`updated_at`。
索引 `(user_id, requested_at DESC)`；推荐部分唯一索引 `(user_id) WHERE consumed_at IS NULL`
保证同一用户只有一个有效链接。

> 不把 token 放 Redis：它是安全凭据，必须可审计、可单次消费、跨重启稳定；明文 token 永不入库。
> 完整流程、冷却/5 次窗口、会话版本、错误码与测试见
> [P01](../../docs/P01-Worklane-规划-2026-10-20.md) §5。

### 3.11 `tasks.updated_by`（000002 新增）

需求文档 5.6 要求组内汇总页能"查看任务最后修改人和最后修改时间"。
时间由 `tasks.updated_at` 提供，但**没有任何列能回答最后修改人是谁**——
`created_by` 是创建者。完整的操作历史属于 Audit（`activity_logs`）阶段；
本列是"当前指针"，让列表与甘特图能在一次查询里给出最后修改人。

语义：`updated_by` 恒等于"最近一次修改 `tasks` 行的用户"，与 `updated_at` 跟踪
**同一个事件**——两者在同一条写语句里一起推进。成员关系与附件不触碰 `tasks` 行，
因此两者都不变。

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 类型 | `UUID NOT NULL` | 任务总是有人创建的，没有"未知"状态；`created_by` 同样是 NOT NULL |
| 回填 | 现有行按 `created_by` 回填 | 生产环境尚未部署，但测试库有数据，迁移必须能原地升级 |
| 删除行为 | `ON DELETE RESTRICT` | 与 `created_by` 一致；本系统的用户一律停用而非物理删除 |
| 索引 | `ix_tasks_updated_by` | 支撑"按最近修改排查"；组内汇总按此列过滤时不必全表扫描 |

不变式由集成测试 `TestTaskUpdatedByAdvancesWithUpdatedAt` 锁住（覆盖创建、PATCH、
改日期、逻辑删除四条写路径，并断言成员变更**不**推进它）。

## 5. Go 迁移文件建议

使用 `golang-migrate` 风格的成对文件：

```text
internal/database/migrations/
├── 000001_init.up.sql
└── 000001_init.down.sql
```

要求：

1. `up` 与 `down` 必须成对且可逆，且**在真实数据库上逐一执行验证**，不能只"写过 down"。
2. 迁移内容必须可重复执行、可审查。
3. 部分唯一索引是本项目的核心不变式，必须在初始迁移中就建立。
4. 禁止在生产库手工修改表结构作为常规流程。

### 5.1 初始迁移要点清单

- 建表顺序：`users` → `groups` → `group_members` → `group_join_requests` → `projects` → `project_members` → `tasks` → `task_members` → `idempotency_keys`。
- 外键删除行为必须显式声明（RESTRICT / CASCADE / SET NULL），不得依赖默认值。
- 所有枚举字段必须带 `CHECK`。
- `project_members`、`task_members` 必须建立 `WHERE role = 'owner'` 的部分唯一索引。
- 日期范围约束 `end_date >= start_date` 在 `projects` 与 `tasks` 上都要有。
- 时间列统一 `TIMESTAMPTZ`（原实现曾出现过 `projects.archived_at` 用错类型的修正，注意不要重犯）。

### 5.2 各模块的迁移归属

**第一阶段至第三阶段的全部模块均已落地**（截至 2026-10-12，迁移 head = `5`；
2026-10-19 注册审核新增 `000006`，2026-10-21 附件存储账本新增 `000007`，当前 head = `7`）：

| 模块 | 迁移 | 说明 |
| --- | --- | --- |
| Users | 无 | 用户资料、时区、提醒开关与状态全部落在既有的 `users` 表上（§3.1），迁移版本当时仍停在 `1`。"管理员至少保留一个"这一不变式由应用层在事务内以行锁保证（见《S02-HTTP接口契约.md》4.3），数据库无法表达"至少存在一行满足条件"这类跨行约束 |

## 6. 验收要求

1. 空库执行全部迁移后，schema 与本文档一致。
2. 迁移 `down` 可回退，且回退后 `up` 可再次成功。
3. 部分唯一索引在真实数据库上被验证**确实拒绝**第二个 owner。
4. 所有 `CHECK` 约束在真实数据库上被验证确实生效。
5. 逻辑删除的默认过滤在**单查与列表两条路径上行为一致**。

## W5 数据模型（000009，2026-10-22）

迁移 head=9，业务表 15 张。`users.session_version INTEGER NOT NULL DEFAULT 0 CHECK >=0`；会话保存登录时的版本，每次解析与数据库比较。升级前会话缺字段按 0；管理员/自助重置均递增。

`password_reset_states`：id UUID PK，user_id UUID UNIQUE FK users ON DELETE CASCADE，last_self_service_reset_at timestamptz NULL，created_at/updated_at timestamptz NOT NULL。

`password_reset_tokens`：id UUID PK，user_id FK users CASCADE；token_hash varchar(64) UNIQUE（64 小写 hex，SHA-256），requested_at/expires_at timestamptz NOT NULL（expires_at > requested_at）；consumed_at/sent_at/failed_at timestamptz NULL，last_error varchar(500) NULL，created_at/updated_at NOT NULL。按 user_id/requested_at DESC 建索引；user_id WHERE consumed_at IS NULL 部分唯一索引保证一个未消费令牌。

所有签发/确认操作先锁 users；邮件发送在提交后，结果另行更新。管理员重置、邮箱字段更新、停用均在同事务消费未使用令牌。无效/过期令牌在 Argon2 前拒绝。登录时升级摘要使用原摘要 CAS，避免覆盖并发重置。

000009 down 删除令牌/冷却状态与会话版本；属于有损回退，需停服务并清空 Redis 会话再切旧版本。密码摘要不会恢复旧值。
